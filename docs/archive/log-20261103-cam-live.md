# 真人摄像头采样 · 2026-11-03 晚（2.8.3）

采集链路：C 画幅相机（28-70）→ **MacroSilicon MS2109** USB2.0 采集卡 → OBS「视频」集合
（画布 1080×1920 竖屏）。近景，脸宽 26–31%。全程无直播，只本机截图。

**本轮四个结论，前两个与美颜算法无关，但比算法问题更影响实际观感。**

---

## 一、采集卡默认格式导致每帧解码失败（最严重，已修）

用户长期反馈「摄像头效果很不好」。日志给出了原因：

```
21:07:42.755: 视频采集设备: Error decoding video
   （伴随 warning: Found EOI before any SOF / fatal: No JPEG data found in image）
```

从 OBS 启动到 21:14:17 约 395 秒内累计 **11856 次**，间隔恒为 32 ms ≈ 每帧一次。
即采集源几乎**每一帧都解码失败**，OBS 只能显示残帧。

### 对照实验（每次改完等 20–25 秒，只数增量）

| 设置 | 20–25 秒内新增解码错误 |
|---|---|
| 设备默认（`res_type=0`，格式「任意」） | **~750（每帧）** |
| 自定义 1280×720，格式仍「任意」 | 175（约 7 次/秒） |
| 自定义 1280×720 + 显式 **MJPEG** + buffering | **0** |
| 自定义 1920×1080 + 显式 **MJPEG** + buffering | **0** |

**结论：关键变量是「显式指定 MJPEG」，不是分辨率。** 默认的「任意」让 dshow
协商到了一个 OBS 解不了的配置（每包都当 JPEG 解，`No JPEG data found`）。
1080p MJPEG 在本卡上完全稳定，不需要降分辨率。

最终设置（已写入集合）：`res_type=1`、`resolution=1920x1080`、`video_format=400`（MJPEG）、
`buffering=true`、`color_space=709`。备份 `视频.json.bak_*`。

> 附带影响：刷屏日志在 7 分钟内写满 3.8 万行，磁盘 IO 也在拖帧。

## 二、画面旋转发生在美颜滤镜之后（结构性错位）

用户在场景里对采集项设了 `rot=-90`，预览正立。但 OBS 的滤镜挂在**源**上，
场景项变换在**滤镜之后**。实测两张同帧截图：

| 图 | 尺寸 | 人脸 |
|---|---|---|
| 场景截图（用户所见） | 1080×1920 | **正立**，脸宽 23% |
| 源截图（滤镜实际输入） | 1920×1080 | **横躺，头顶朝右** |

也就是说五官几何按「眼睛在上、法令纹在下」的假设去套一个横着的脸。
插件不支持旋转输入（`setDetectOptions(rotate,...)` 的 rotate 参数在实现里被忽略，
`beauty_core.cpp:1434` 第一个参数无名），`mirror` 只能水平翻转。

### 解法：插一层子场景，让旋转发生在滤镜之前

```
采集源 --(子场景内 rot=-90)--> 子场景 CamRot --(OBS美颜滤镜)--> 父场景
```

- 工具：`05_验证/cam_rot.py --apply|--revert`
- 父场景原采集项**保留并隐藏**，原源上的滤镜**只禁用不删除** → 一键回滚
- 实测有效：新会话日志出现 `性能 1080x1920 … S/T/R/D/W=180/0/0/0/0`，说明滤镜在
  子场景上正常渲染（当轮只开磨皮，故只有 S 段认领）

## 三、真人近景：祛斑 100 无效，磨皮 60 有效

### 为什么不能用逐像素对拍

相机是 AF（用户一人无法手动对焦），实测**同一组参数、相隔 0.6 秒的两张图**，
就有 56% 像素差 >2 灰阶、平均差 3.3；脸区内组内噪声 2.4–6.1 灰阶。在这个底噪下：

| 比较 | 平均差 | 判定 |
|---|---|---|
| raw vs spot40 | 3.96 | **落在噪声内** |
| raw vs all | 11.19 | 明显超出 |

### 改用对位移不敏感的指标：脸区高频能量

斑点尺度对应 0.5–2 px 的细节，祛斑若生效必然压低这部分能量。每组 4 张取中位数：

| 组 | 拉普拉斯方差 | 局部对比(std of 原图−3×3均值) | 相对 raw |
|---|---|---|---|
| raw（关滤镜） | 9.8 | 0.95 | — |
| **spot100（祛斑拉满）** | **10.0** | **0.96** | **0（无变化）** |
| blur60（磨皮 60） | 8.3 | 0.86 | **−14%（能检出）** |

**阳性对照成立**（磨皮被同一指标检出 −14%），目标项为 0 → 祛斑在真人近景上
**确实不产生任何可见变化**，与 §9.20.3 的代码级推断（`bounds_` 被清空 → 两条路径
都不执行）一致。

### 一处作废的对照

`BEAUTY_MASK_GEOM_ONLY=0` 那一轮，日志仍报 `gonly=180`，开关**未按预期生效**，
该轮不能作为「关掉 geomOnly 后祛斑就有效」的证据。原因未查（时间不够）。
**不影响上面的结论**：祛斑无效是用户可见事实，不依赖机制归因。

## 四、工具坑

1. **`SaveSourceScreenshot` 不含场景项变换**。截「源」得到的是滤镜输入，截
   「场景」得到的是用户所见 —— 两者方向不同正是「旋转在滤镜之后」的直接证据。
2. **`SetSceneItemTransform` 传 `boundsWidth=0` 会报 402**（下限 1.0）。只描画要改的
   字段即可。
3. **`CreateSceneItem` 后立刻 `GetSceneItemList` 可能查不到**，用返回值里的 id。
4. 相机 AF 漂移是这类实验的固有噪声，**逐像素对拍在真机上不可用**；要么锁曝光/对焦，
   要么改用统计指标 + 阳性对照。
5. `GetSourceFilterList` 的字段是 `filterName`/`filterEnabled`，不是 `name`/`enabled`。
