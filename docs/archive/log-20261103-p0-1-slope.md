# P0-1 S5 斜率判定记录（2026-11-03）

## 一、测法

`py -3 05_验证/slope_smooth.py --rounds 3`，用 `BEAUTY_SMOOTH_PASSES` 把磨皮趟数锁成 1/2/3，各跑 3 轮、每轮 25 s，两档共 18 次起停。
趟数与 draw 的对应关系（脚本内置）：`draw = 5 + 6 × 趟` → 11 / 17 / 23。

被测 DLL：`BA5363F30075FE1B735C2E0C37733952`（`v2.7.1, engine=gpu/2.0.0`）。

## 二、数据（磨皮段毫秒，3 轮中位数）

| 分辨率 | 趟=1 (draw 11) | 趟=2 (draw 17) | 趟=3 (draw 23) | 拟合（磨皮 = a + b×draw） | 每 draw |
|---|---|---|---|---|---|
| 1280×720 | 0.21 | 0.22 | 0.22 | 0.19 + **0.0012**×draw | **1.2 µs** |
| 3840×2160 | 1.25 | 1.27 | 1.37 | 1.13 + **0.0100**×draw | **10.0 µs** |

脚本给出的分解（23 draw 时）：

- 720p：提交/切换 **0.03 ms（占 13%）**，随像素走的 GPU 项 0.19 ms（87%）
- 4K：提交/切换 **0.23 ms（占 17%）**，随像素走的 GPU 项 1.13 ms（83%）

原始每轮读数：720p 依次为 (0.20/0.21/0.23)、(0.21/0.23/0.22)、(0.21/0.22/0.22)；4K 依次为 (1.21/1.33/1.25)、(1.27/1.35/1.25)、(1.23/1.42/1.37)。

## 三、这对 S5/S6 意味着什么

**S5 通道打包**的目标是把 draw 从 23 压到 ≤15。按实测斜率：

- 4K：省 8 draw × 10.0 µs = **0.080 ms**。磨皮段 1.37 → 1.29（−5.8%）；往返 2.42 → 约 2.34（**−3.3%**）。
- 720p：省 8 draw × 1.2 µs ≈ **0.010 ms**，往返降幅约 **−1%**，落在噪声内。

原定门槛是「4K draw 段与往返相对 S4 再降 **≥30%**」。实测上限差一个数量级。即使把全部 23 个 draw 的提交/切换开销归零（0.23 ms），往返也只降 **9.5%**。

**S6 去两趟 Copy**（draw 23→21）按同一斜率只省 **0.02 ms**（4K，约 0.8% 往返）。它便宜（0.5 d）但收益同样在噪声边缘。

**建议**（非结论，待你拍板）：

1. S5 按「斜率≈0 / 像素主导」分支处理 —— 砍掉，省 3–5 天；
2. S6 从"必做"降级为"顺手做"，理由写在计划里改成"接口清理，收益不计"；
3. 重心移到 S7（CPU 功耗 0.42 → ≤0.2 核）—— 它是唯一还能拿到数量级收益的方向。

## 四、一个存疑点（需你确认）

`04_文档\开关总表.md` 第 61 行写 `BEAUTY_SMOOTH_PASSES` 的默认说明为「不设即正常 **5 趟**」，但源码 `01_源码\beauty_smooth.h:343` 是 `int passes = 3;`（`beauty_core.h:44` 注释亦写"默认 3"），只有诊断开关才会覆盖。按源码，生产 draw 应为 23（与计划文档的基准一致）。

**我的判断**：开关总表那句是笔误，应改为「正常 3 趟」。但这只是我的推断，未找到起草依据，请你确认后再改。

## 五、一个必须说清的局限

本次只用 1–3 趟，未测 4–6 趟。若将来把生产趟数调高，draw 上升、提交/切换占比会随之上移，本记录的斜率仍可用（线性项不变），但"占比"会变。
