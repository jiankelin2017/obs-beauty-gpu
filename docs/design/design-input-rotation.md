---

## 1. 背景与问题

用户的真实竖屏摄像头链路：采集卡输出 **1920×1080 横屏**（脸在画面里是横躺的），用户在 OBS 场景项上设 `rot=-90` 让显示变竖屏。

缺陷（§9.20 已定位）：场景项变换只作用于**显示合成**，滤镜拿到的源纹理 `in_tex` 仍是未旋转的 1920×1080。于是：

- 检测（YuNet）在横躺的脸上跑，FaceBox / kps 全部错位；
- 五官几何（眼/眉/法令纹/嘴）、美形（瘦脸/大眼/下巴）、保护椭圆全部按错位置落笔；
- 当时用「插子场景 CamRot 把旋转移到滤镜之前」绕开，但那是临时工程 hack，不是产品能力。

`beauty_core.cpp:1434` 的 `setDetectOptions(int, ...)` 在 GpuEngine 里把 `rotate` 参数直接丢弃，也印证了旋转从未进入管线。

---

## 2. 目标与范围

**目标**：面板新增「输入方向 0/90/180/270」下拉；用户设为非零后，滤镜**在管线内部**把输入当作旋转后处理，使检测几何、五官、美形、保护全部对齐到正确人脸位置。**用户保留原有的场景项旋转做显示**（输出朝向不变）。

**范围内（做）**：
- 面板新增下拉 `input_rot`（0/90/180/270，默认 0）。
- 检测缩略图按 `input_rot` 旋转采样（letterbox/draw 步）。
- 检测出口的 FaceBox / kps 反变换回源坐标系（纯函数）。
- 验证：旋转场景下 mask/五官/美形落点正确。

**范围外（不做）**：
- 不旋转**输出像素**。滤镜输出仍是源朝向（横屏），由 OBS 场景项旋转负责显示竖屏。这样输出尺寸、23-draw 渲染目标、mask/protect 缓冲全部保持 `Ws×Hs`，改动面最小。
- 不做任意角度（只 90 的倍数），避免双线性重采样引入的几何精度问题。

---

## 3. 核心思路

只在「检测几何」这一条路上引入旋转感知，**渲染与输出完全不动**：

1. **旋转检测输入**：宿主把 `in_tex` 绕中心旋转 θ 后 letterbox 进 `thumb_rt`（S×S）。检测看到的因此是「正立的脸」。
2. **缩略图语义改成「旋转后全帧」**：`beautyCoreSetThumbSource(..., fullW, fullH, ...)` 的 `fullW/fullH` 传**旋转后的尺寸**（θ=90/270 时 `Wr=Hs, Hr=Ws`；θ=0/180 时 `Wr=Ws, Hr=Hs`）。`scale/ox/oy` 仍按 letterbox 正常算，只是针对 `Wr×Hr`。
3. **检测出口反变换**：引擎拿到 FaceBox/kps（旋转后全帧坐标）后，用一个**纯函数** `invRotateFace()` 把它们绕中心转回 `-θ`，映射到源坐标系 `(Ws×Hs)`。这一步之后，mask / protect / 五官椭圆 / 美形 warp 一切照旧在源坐标工作。
4. **渲染与输出**：`process(w,h)` 收到的仍是 `Ws×Hs` 源帧，mask/protect 仍在 `Ws×Hs` 上构建，23-draw 渲染、输出纹理尺寸全部不变。

> 为什么输出不动：用户已习惯用场景项旋转显示。若滤镜同时旋转输出，会和场景项旋转叠加成双重旋转。把「旋转」从场景项吸收进滤镜输入，是产品级正确解法；显示旋转继续留在场景项。

---

## 4. 坐标变换数学

设源帧 `Ws×Hs`，旋转角 `θ ∈ {0,90,180,270}`。旋转后全帧尺寸：
- θ=0 / 180：`Wr=Ws, Hr=Hs`
- θ=90 / 270：`Wr=Hs, Hr=Ws`

检测在「旋转后全帧」坐标系工作，FaceBox 中心 `(cx,cy)`、关键点 `kps[]` 均在该系。反变换把点映射回源系：

```
C_rot = ((Wr-1)/2, (Hr-1)/2)      // 旋转后全帧中心
C_src = ((Ws-1)/2, (Hs-1)/2)      // 源帧中心
P_src = R(-θ) · (P_rot - C_rot) + C_src
```

其中 `R(-θ)` 为标准 2D 旋转矩阵。box 的宽高在 θ=90/270 时互换（`w_src=h_rot, h_src=w_rot`），θ=0/180 时不变。

`invRotateFace(FaceBox& f, int theta, int Wr, int Hr, int Ws, int Hs)` 同时对 `f.cx/f.cy/f.w/f.h` 与全部 `f.kps[]` 做上述变换；`kpsSane()` 等后续判定在变换后执行即可。

## 6. 验收方案

1. **单元级几何对拍**：构造一张「横屏里横躺的正脸」素材，设 `input_rot=90` 跑检测，导出 `faces[0]` 的 `cx,cy,w,h,kps`；手工把同一张图在 Python/OpenCV 里 `rot90` 后独立跑 YuNet，比对两者在**源坐标系**下的 FaceBox/IoU 与 kps 距离（应 ≤1 px）。
2. **mask 落点可视化**：开 `BEAUTY_MASK_GEOM_ONLY=1` + `BEAUTY_SPOT_DEBUG`/mask dump，肉眼确认旋转 90 后眼睛/嘴保护椭圆落在横躺脸的正确位置（不再整体错位）。
3. **端到端真机**：复用 §9.20 的 `CamRot` 子场景拆除，回到「源设 rot=-90 + 滤镜 input_rot=90」组合，截图确认五官/美形对齐；关掉场景项旋转、仅 input_rot=90 也应得到正立输出（两种都验证一次）。
4. **回归**：`input_rot=0` 全量回归 2.9.1 基线（S0 基线、4K 祛斑像素量），确保默认路径零差异。
5. **判定门槛**：旋转场景下 IoU ≥ 0.95、kps 中位误差 ≤1 px；`input_rot=0` 与 2.9.1 逐字节一致（maxdiff 0）。

## 7. 风险与回滚

- **缩略图旋转绘制**：`gs_matrix_*` 绕中心旋转 + letterbox 矩形互换，是宿主端最易错的环节；先单独用 `BEAUTY_THUMB_DUMP` 落盘旋转后缩略图肉眼核。
- **反变换方向**：务必是 `-θ` 且 box 宽高互换正确；用 §6.1 的 OpenCV 独立复算兜底（不要拿注释当证据，见 §9.12.4 教训）。
- **90/270 尺寸互换**：任何 `Wr/Hr` 用反都会让几何系统性偏移一整帧；`process(w,h)` 的 `w,h` 始终是源尺寸，反变换的输入/输出尺寸必须严格区分。
- **回滚**：`input_rot` 默认 0，出问题只需把下拉设回 0 即回到 2.9.1 行为；开关本身不污染默认路径。

## 10. 3.2.0 自动输入方向认定（2026-11-06）

### 10.1 为什么要做

2.15.2 删掉面板下拉之后，唯一入口变成 `BEAUTY_INPUT_ROT` 环境变量。但**普通用户不会去设环境变量**，
于是「采集卡输出 1920×1080 横躺 + 场景项旋转成竖屏」这种最常见的竖屏机位接法，表现为
「美颜完全没效果」，或者「效果冻在横屏、拉滑块不响应、美白失效」。

2026-11-06 的用户日志把两种表现都录到了：

```
17:53 render#0 target=色度键 1080x1920 … frame#0 drawn 1080x1920 faces=0 noface=0
17:54 仅色彩层：磨皮=0 清晰=0 美白=100｜引擎掩码 px=0 有脸=1 无脸帧=354
```

判据很干脆：源分辨率 1920×1080、滤镜入口 `target=… 1080x1920`、`faces=0` 持续 —— 人脸检测
在躺倒的脸上一个框都出不来，掩码为空，所有效果乘 0。

### 10.2 判据与状态机

| 环节 | 规则 |
|---|---|
| 资格 | 「用户没声明方向」（`input_rot == 0`，由渲染线程刷成原子量 `autoRotAllowed_`）且当前有效方向 `effRot == 0` 且本帧检不到脸 |
| 计数 | 每发生一次「检不到脸」`autoMiss++`；达到 `BEAUTY_AUTO_ROT_MISS`（默认 20）触发一次试探 |
| 试探 | 在**同一张输入图**上各跑一次 90° 与 270° 重采样检测，先试哪个按轮换（`autoProbeNext_` 交替），避免固定顺序让另一半接法每轮多付一次推理 |
| 命中 | 哪个方向出脸就 `setEffRot(该角度)`，此后全帧路径按该方向重采样检测，几何再经 `invRotateFace` 反变换回源坐标 |
| 未命中 | `autoCool = BEAUTY_AUTO_ROT_COOL`（默认 60 次检测 ≈ 3 秒）后才允许下一次试探，没人时不至于每轮都烧推理 |
| 作废 | 换源 / 换分辨率 / 用户改声明方向 → 渲染线程只投一个 `rotAutoReset_` 原子信号，计数器由检测侧在下一轮 `buildMaskInto` 入口自己清（详见 §10.7） |

命中后**不再单独存一份「自动认定的角度」**：唯一真相就是 `effRot_`。3.2.0 曾同时维护
`autoRot_` 与 `effRot_`，前者只写不读，等于一个必然漂移的副本，本次已删除（见 §10.7）。

### 10.3 三个设计取舍

**只试 90/270，不试 180。** 180°（上下颠倒）在直播场景里没有对应接法——摄像头不会倒装；
而试三个方向的代价是 50% 更多试探推理。需要 180° 的场合仍走 `BEAUTY_INPUT_ROT=180` 手工路。

**试探用的是「同一张输入图」，不是下一帧。** 若等下一帧再试，人一动就把失败原因混进来了
（可能是刚才那帧真的没人）；同图重采样保证「唯一的变量就是方向」。

**命中后改走全帧路径，不用检测缩略图。** 缩略图在宿主侧按面板方向转，方向认定发生在引擎内部，
两边一旦不同步，缩略图就是「转过一次的图再转一次」，检测会永久失败。改走全帧让引擎自己按
`effRot` 旋转重采样，代价是每帧多一次整帧回读。**实测代价可接受**：2026-11-06 直播中
（1080×1920@30，美颜+录制+推流同时）渲染帧平均 5.8 ms、因渲染延迟丢帧 0/23620，故
「按认定方向转检测缩略图」的省流量优化判定**不做**。

### 10.4 验收

**离线判据** `06_离线验证/_autorot_probe.py`，三条：

| 用例 | 期望 | 结果 |
|---|---|---|
| 躺脸 720×1280（`face_front_720p_r90.png`）+ 方向未声明 | 自动命中 90°，之后 `faces=1` | 第 95 帧认定 90°，第 100 帧起出脸 |
| 正立脸 1280×720 | 40 帧内始终 `effRot=0`、`faces=1` | 通过，无误判 |
| 纯色空画面 | 120 帧内始终 `effRot=0` | 通过，没人时不乱锁方向 |

对照实验（同一张躺脸素材，手工设方向）：`input_rot=0` → `best=0.456`（低于 0.6 阈值，检不出）；
`=90` → `faces=1`、掩码 21.96%；`=270` → `faces=1`、掩码 24.26%。

**真机验收**（2026-11-06 18:02，用户直播中）：

```
18:02:03.601 [美颜] 连续 20 次检不到脸，自动方向探测命中 270°…下一帧起改走全帧路径
18:02:03.639 掩码路径：mask=gpu geomOnly=1 gpuMask=1 count=1 … roi=1049,479,1325,859
```

从加滤镜到命中 **1.13 s**；命中后 38 ms 内检到脸，用户确认磨皮滑块有反应、美白可见。
该机位实际是 **270°**（不是设计时预估的 90°），说明两个方向都试是必要的。

### 10.5 开关与回退

|---|---|---|
| `BEAUTY_AUTO_ROT` | 开 | `=0` 逐字节回到 3.1.x 行为（离线确定性对拍须用它） |
| `BEAUTY_AUTO_ROT_MISS` | 20（≈1 秒） | 触发阈值，合法 3–600 |
| `BEAUTY_AUTO_ROT_COOL` | 60（≈3 秒） | 试探冷却（按检测次数），合法 0–6000 |

三个开关的完整口径见 [`../reference/reference-switches.md`](../reference/reference-switches.md)。

### 10.6 顺带修掉的缺陷

`warmUp()` 原本没有幂等保护：离线台每帧调用一次 `ensureReady`，就把 `mask_` 重置成固定的
1920×1080、并把检测缓存压回 999，于是探测计数器每帧被清零、自动方向永远触发不了。
这个缺陷一直藏在「离线台跑得慢」的表象里，直到本次调试才暴露。修法是加一次性守卫。

### 10.7 审查后修正：并发约定与预热标记（3.2.2 已发布）

> 本节描述的修正已随 **3.2.2** 发布，`BEAUTY_BUILD_STR` = 3.2.2。
> 同批还修了一个与本主题无关但同样严重的缺陷（删滤镜再加回来 → 异步 worker 不重启），
> 见 [`../CHANGELOG.md`](../CHANGELOG.md) 3.2.2 与 [`../adr/adr-multi-instance-slots.md`](../adr/adr-multi-instance-slots.md)。


3.2.0 的设计文档写了「`buildMaskInto` 只读 src、不碰任何成员，所以异步时不需要加锁」。
自动方向探测破了这条契约：它在 `updateMask`（渲染线程）里直接清 `autoMiss_/autoCool_/
autoProbeNext_/autoProbeLogged_`，而同一个 `updateMask` 在异步路径上会把活交给 worker，
worker 正在 `buildMaskInto` 里累加同一批变量。换源/换分辨率那一帧两线程同时写，属 UB
（x86 上对齐 32 位写不会真撕裂，所以线上没炸，但这是运气不是设计）。原注释里
「与 `asyncOn_` 互斥」也不成立：`async_.m` 只保护帧槽，不保护这几个计数器。

修法是把「清计数」从跨线程写改成**单向信号**：

| 角色 | 做什么 |
|---|---|
| 渲染线程 | 只在换源/换分辨率/改声明方向时 `rotAutoReset_.store(true)`；另外每帧刷 `autoRotAllowed_`（`input_rot==0`）。两者都是原子量 |
| 检测侧（worker 或同步时的渲染线程） | 在 `buildMaskInto` 入口 `rotAutoReset_.exchange(false)`，命中了才清那四个计数器。清点与用点在同一条线程上 |
| 宿主 | 只读 `effRot_`（原子量）决定要不要转缩略图，不碰任何计数器 |

顺带三处：

1. **删掉 `autoRot_`**。它只写不读，是 `effRot_` 的影子副本；留着的唯一效果是让人以为
   「自动认定的角度存在两处」，日后必然有人只改一处。
2. **`release()` 复位 `warmed_`**。不复位的话，重新启用滤镜会重新加载模型却跳过预热，
   3.1.21 花力气消掉的「开滤镜卡首帧」（≈20 ms）会回来 —— 而且正好落在用户拨开关那一刻。
3. **`warmed_ = true` 移到 `warmUp()` 末尾**。原来写在三笔 8 MB `assign` 之前，
   一旦抛 `bad_alloc`，这个实例就永远不再预热而首帧成本照付，比不幂等更糟。

回归证据：`_autorot_probe.py` 三条判据结论不变（第 95 帧认定 90°、第 100 帧出脸；
正立脸与空画面均不误判），`offline_regress.py check` 四条 golden 仍逐字节相同。
