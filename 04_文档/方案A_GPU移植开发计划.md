### 0.2 实际架构与原计划的偏差（必须知道，否则会照着旧图施工）

| 项 | 原计划 | 实际做法 | 为什么改 |
|---|---|---|---|
| GPU 入口 | 新增 `processGpu(slot, in_tex, out_tex)`，整帧进出纹理 | **引擎内回调** `beautyCoreSetSmoothHook()`，按算子逐个接管 | 掩码↔帧对齐在 `process()` **内部**才把 `src` 换成上一帧，外侧接管必然错帧（实测 71% 帧如此） |
| 着色器 | 6 个：tone / blur_sep / skin / blend / warp / detail | **2 个**：`tone.hlsl`（单 pass 做完清晰+美白+红润）、`smooth.hlsl`（5 technique 串联） | 磨皮可分离近似把 blur/skin/blend 合成了一条链，少 4 个文件、少 4 次纹理往返 |
| 中间纹理 | 未定 | 半分辨率 **RGBA32F 装 0..255 浮点** | CPU 的 `surface3RgbBand` 全在灰阶域运算；0..1 归一化会让盒宽/强度换算全错 |
| 顺序 | 按算子平行推进 | **按「CPU 代价 ÷ 往返代价」排序**，磨皮先上 | 4K 下磨皮占引擎 87%，其余算子加起来不到 13% |

### 0.3 3.1.50 测出的新事实（改变了后续优先级）

720p 把磨皮段 1.74 ms 拆开后：

| 段 | ms | 占磨皮 | 含义 |
|---|---|---|---|
| 掩码交错 + `gray_tex` 上传（含对齐帧的整帧上传） | 0.552 | 31.8% | **未单独埋点**，是推算的差值 |
| `draw`（23 次 draw 的**命令提交**） | 0.038 | 2.2% | GPU 计算几乎免费 |
| `map`（排空队列 + 下载 3.7 MB） | 0.813 | 46.8% | **真瓶颈** |
| `copy`（3.7 MB memcpy 进 `dst`） | 0.336 | 19.3% | 纯带宽 |

**结论改写了两条原假设：**

1. **「优化着色器省 GPU 算力」基本没有收益** —— 23 次 draw 提交只要 38 µs。原计划里「减少 pass 数」的优先级应下调。
2. **瓶颈是搬运，不是算力。** 磨皮段 96% 的时间花在数据进出显存上。这让 Phase 5（全链路不出 GPU）从「架构洁癖」变成了**唯一能再降一个数量级的手段**，同时新增一个便宜的前置项：
   - **3.7（已做半项）传输优化**：掩码从一张 R8G8 拆成两张 R8，省掉每帧一趟 1.8 MB 的 CPU 交错写（3.1.51）。「对齐换帧复用上一帧纹理」复核后**撤单**，理由见 6.2②——held 帧是**新内容**不是重播，复用要赌帧序，错了会静默显示旧帧。
3. **「4K 的结论」已于 3.1.54 补齐（原阻塞项关闭）** —— 像素比 9.00 时
   `draw` 只涨 **1.75×**（0.04→0.07 ms），而 `map` 6.93× / `copy` 10.55× /
   `prep` 10.88× / `掩码` 9.10× / `上传` 10.96× / 整帧 7.69× —— **除 `draw`
   与亚线性的 `下载`（5.23×）外，搬运项全部随像素增长**。
   这坐实了「draw 量的是提交时间不是 GPU 计算时间」，也证明 **5b 的收益随分辨率放大**。
   4K 整帧中位 **32.24 ms**（158 窗口，24.48~39.07）—— **中位在 30 fps 的
   33.3 ms 预算内，但峰值 39.07 超出**，且 4K 的 `D` 位大量小于 `chain`（含 0）、
   细节段认领不稳（成因未查明）。**4K 尚不稳态，5b 是提稳与提速的前提。**
   ⚠ 日志读取时 `obs64` 仍在运行、窗口数还在追加，中位数过 110 窗口后趋于稳定，
   最终以退出后复跑为准。详见第十节与 `05_验证/analyze_4k_ratio.py`。

## 一、目标与动机

- **主目标**：把占 CPU 大头的逐像素运算（磨皮 / 美白 / 红润 / 清晰 / 五官立体 / 美型 / 细节回填）从 CPU 多线程搬到 GPU，让画面全程留在显存，消灭 `gs_stage_texture → gs_texture_map`（D3D11 Map 同步等待）→ CPU 处理 → `gs_texture_set_image` 上传的往返。
- **功耗动机**：CPU 负载下降后，DVFS 主动降频降压，CPU 功耗 ∝ 占用^α（α≈1.2–1.5），降幅大于占用降幅。人脸检测已走 DirectML GPU，无需动。
- **非目标**：不动人脸检测（已 GPU）；不做纯 DirectML 算子图（见第四节，方案 B 更贵更险）；不删 CPU 引擎（保留作兜底 + 回归 golden）。

## 二、架构总览（GPU 主 + CPU 辅 / 兜底）

```
OBS D3D11 纹理
   │  (不下载 CPU)
   ▼
[GpuBeautyEngine::processGpu]  ← 新增，实现 IBeautyEngine
   ├─ Pass1 tone.hlsl      美白/红润/清晰/五官立体(+region mask)   → 色调纹理
   ├─ Pass2 blur_sep.hlsl  可分离高斯(横/竖)                       → 模糊纹理
   ├─ Pass3 skin.hlsl      引导/表面3混合 + 振幅门控               → 磨皮纹理
   ├─ Pass4 blend.hlsl     按皮肤掩码 + 强度 t 混合原图            → 混合纹理
   ├─ Pass5 warp.hlsl      按位移图重采样(瘦脸/大眼/下巴)          → 变形纹理
   └─ Pass6 detail.hlsl    细节回填(加回高频/锐化)                 → 输出纹理
   ▼
回 OBS 绘制
```

**CPU 在稳态下只做（"辅"）：**
1. 人脸检测主机侧后处理：从 ONNX(DirectML) landmarks 算**位移图**与**皮肤掩码**（小数据，缓存），上传为纹理/常量缓冲；
2. 每帧准备着色器**常量缓冲**（参数、区域参数）；
3. OBS 胶水（取帧、读面板参数、绘制）。

**CPU 引擎（core 1.4.0）保留为：**
- `BEAUTY_GPU=0` 或 `auto` 探测失败时的**兜底**；
- GPU 每个算子改写完后的**逐像素 golden 对拍基准**（守 79.0 复刻分）。

## 三、关键技术决策

| 决策点 | 结论 | 理由 |
|---|---|---|
| GPU 后端 | **D3D11 HLSL 着色器**（像素/计算），非纯 DirectML | OBS 是 D3D11，DirectML 跑 D3D12 需 D3D11↔D3D12 互操作，复杂度×2、风险高；DirectML 是推理框架，表达逐像素算子别扭 |
| 人脸检测 | 保持现有 DirectML（已 GPU） | 不动、不回退 |
| 引擎接口 | 扩展 `IBeautyEngine`，新增 `processGpu(slot, gs_texture_t* in, gs_texture_t* out, ...)` | CPU 引擎也实现它（内部下载→CPU process→上传），统一调用面；兜底零成本 |
| 资源生命周期 | 每 slot 的 GPU 中间纹理/常量缓冲随源 resize 重建，复用 `obs-beauty.cpp` 现有 `f->stage/out_tex` 管理套路 | 防泄漏、防 resize 崩溃 |
| 开关 | `BEAUTY_GPU` 环境变量（0/1/auto，命名对齐 DaVinci 端）+ 面板"渲染后端"下拉 | auto=探测 D3D11 compute 可用性，失败回 CPU |
| 量化对齐 | 每算子 A/B 对拍（CPU 当 golden，diff 阈值），必要时定点近似 | 守 79.0 分与 11 项对齐 |

## 四、引擎接口改造（beauty_core.h / beauty_core.cpp）

> ⚠ **这一节已被实际实现取代，别照着施工。** 原计划新增 `processGpu(in_tex, out_tex)` 整帧进出
> 纹理；实际改成了**按算子接管的钩子** `beautyCoreSetSmoothHook(fn, user)`，因为掩码↔帧对齐
> 会在 `process()` **内部**换帧，外侧接管必然错帧。保留此节只为记录当初的推演过程。
>
> 3.1.52（Phase 5a）把它再往前推了一步：`beautyCoreSetChainHook(fn, user)` 不接管「一个算子」
> 而是接管「一段连续区间」（返回段位掩码），中间结果全程留在显存。`processGpu` 那种「整帧
> 进出纹理」的形态只在 5b（链尾不回读）才真正需要 —— 那时引擎的 `process()` 契约要改成
> 接受/返回纹理，而不再是「写满 dst」。

当前：`virtual bool process(int slot, const unsigned char* src, unsigned char* dst, ...)`（CPU 路径，glue 先下载再调）。

新增（不影响现有 CPU 路径）：
```cpp
// 在 IBeautyEngine 中新增
virtual bool processGpu(int slot, void* in_tex, void* out_tex,
                        int w, int h, const BeautySettings& s) = 0;
```
- `CoreEngine`（CPU）：`processGpu` 内部 `gs_texture_map` 下载 → 原有 `process` → `gs_texture_set_image` 上传。**行为与现有一致，保证兜底等价。**
- `GpuBeautyEngine`（新增 `beauty_gpu.cpp` + `beauty_gpu.h`）：原生在纹理上跑着色器，全程不回 CPU。
- `obs-beauty.cpp`：`BEAUTY_GPU != 0` 时改走 `processGpu`（不下载）；`== 0` 时仍走原 `process`。

**磨皮的关键实现约束（下一个人必须知道，写错就要重来）：**

1. **必须按 `surface3RgbBand` 的双尺度带通抄**，不是按 `C23` §3.1 的 25 tap 抄——后者已被 §10.4 的频响实测证伪。
2. **中间纹理用 RGBA32F 装 0..255 浮点**，不是 0..1。两个换算点：Down ×255、Comp ×(1/255)。
3. **盒宽按全帧名义宽度算**（`UV` 固定），不能按 ROI/处理域宽度算，否则脸越小半径越小。
4. **钩子必须挂在引擎内**，不能挂主路径外侧（对齐换帧在 `process()` 内部发生）。

**5a 的实现要点（写错就要重来）：**

1. **钩子必须是「段区间」而不是「多挂几个钩子」**。色调/细节的输入是上一段的输出，
   中间只要落一次 CPU 就得重传，白干。所以 `BeautyChainHook` 返回**段位掩码**，
   引擎按 `SMOOTH→TONE→REGION→DETAIL→WARP` 顺序执行并跳过被认领的段。
2. **认领必须是执行顺序上的前缀**，引擎侧强校验。否则「认领细节却跳过五官」会让
   五官段拿到没回读的 `dst`，等于用上一帧的画面 —— 静默错帧，最难查。
3. **参数由引擎算好递出去**（`BeautyChainJob.detail`）。细节的 `fine/mid/thr/knee`
   不是面板值，`beta` 还取决于运动 EMA 状态；宿主自己算一遍必然与 CPU 漂移。
4. **无掩码时细节的掩码语义与磨皮相反**：磨皮当 m=255（全皮肤），细节当 **m=0**。
   跟着磨皮写会让「这一帧没检出脸」时全局锐化整段失效（参考实现 3.0.13 的老 bug）。
5. **时序 EMA 的历史必须两边各自维护、各自作废**。GPU 用一张显存纹理，一旦某帧
   没跑 GPU（回退 CPU / 面板关了锐化），下一帧必须按 copyOnly 重置，否则拖影。
6. **段与段之间必须照样 8bit 量化**（`floor(+0.5)` / `floor`），否则「链式」的结果会
   随段数偏移，逐像素对拍立刻失效。CPU 每段都写回 `unsigned char`，GPU 也必须。
7. **挑渲染目标要比较 `gs_texrender_t` 对象，不能比较 `gs_texrender_get_texture()`。**
   texrender 的纹理由 `begin` 现建，首次 `begin` 之前 `get_texture()` 返回 **NULL**。
   3.1.52 就是拿它判空，于是「色调没开 → `chain_rt` 从未 begin → 判为不可用 →
   细节段整份 return NULL」，5a 收益全丢。这一条对后续 5b/5c 同样成立。
8. **effect 参数要在第一次 draw 之前全部有值。** OBS 的 effect 参数整份共享，
   每个 pass 的 `device_draw` 都会检查**全部**参数；少一个就每帧刷一条
   `Not all shader parameters were set`。不致命，但会把真错误淹掉。
9. **effect 参数是「一次性」的：`gs_technique_begin_pass()` 提交后会消耗掉值，
   同一批值不能连画多趟。** 所以要么每趟重绑，要么别指望「先绑一次全家共用」。
   3.1.52 / 3.1.53 两版都栽在这里，靠「3517 : 1539 ≈ 4 : 3」这个比例才推出来
   （等于「几趟没绑」）。`image` 一直没出问题，正因为它本来就每趟重绑。

## 九、风险登记

1. **量化对齐回退（最高）**：GPU 浮点顺序不同，保边/引导滤波易漂。对策：每算子 A/B 对拍（CPU golden），必要时定点近似。
2. **资源生命周期**：每 slot GPU 纹理/常量缓冲随 resize 重建、旧资源释放。对策：复用 `f->stage/out_tex` 管理套路。
3. **跨帧状态**：异步人脸检测 worker + 区域缓存 + 掩码池仍有状态。对策：检测仍 CPU 小数据，landmarks/mask 传 GPU。
4. **OBS 后端版本**：OBS 30 仍 D3D11；需确认 OBS 31 是否转 D3D12（影响 `gs_get_device` 取法）。
5. **可调试性**：GPU 出错难定位。对策：每 pass 后接一次 stage 回读 self-check（复用现有机制）。
6. **功耗反作用（需预期）**：GPU 负载从 0 起，平台总功耗净降但通常小于 CPU 单项降幅；若目标是笔记本电池，净收益打折扣，但 CPU 温度/风扇确定性利好。

**风险登记的五处修订（实测后）：**

- 原风险 1「量化对齐回退」**部分缓解**：`tone` / `smooth` 两个算子都落在 `maxdiff=1`
  （浮点末位），说明「按 CPU 算法逐项抄」这条路是通的。
  ⚠ **但 `detail` 至今没有任何 GPU↔CPU 对拍** —— 3.1.53/3.1.54 的
  `S/T/R/D/W=180/0/0/180/0` 只证明「细节段被认领且没报错」，**不证明算得对**。
  4K 那趟也一样：只有磨皮/色调对拍行，没有细节对拍行。真要上生产必须先补
  `GPU 细节对拍`，否则「锐化强度对不对」只能靠肉眼。这是**已知未验证项**。
- **风险「性能目标被误设」已被 4K 实证坐实**：原计划把「减少 GPU pass 数」当优化项，
  720p 只有单点（38 µs）时还无法证伪；4K 给出第二点后 `draw` 只涨 1.75×
  （绝对值 30 µs）。**合并 pass 这条路彻底作废，真正的成本是随像素线性的搬运**。
  5b 的收益因此随分辨率放大，不再靠想象。
- **新增风险：跨会话比较会给出假回归。** 3.1.53 单趟自身漂移 3.39→3.76 ms，
  3.1.54 的 4.19 ms 里连未改代码的 `掩码` 段都翻倍。**只比同一会话内的相邻窗口**，
  版本间的绝对性能数字不能直接相减。
- **新增风险：段区间钩子的「静默错帧」。** 认领不是前缀时引擎会整份丢弃（只变慢），
  但宿主侧的**状态**（细节的 EMA 历史）必须跟着作废，否则下一帧会拿陈旧历史做混合。
  3.1.52 的作废点是 `render()` 里「本帧没认领 DETAIL → `det_hist_ok = false`」，
  以及引擎侧的 `detailEmaReset_ = true`。以后加新的有状态段（美形缓存、五官椭圆）
  必须同样处理。
- **新增风险：`gs_texrender_t` 的首次 begin 语义。** 3.1.52 的实测失败（5a 收益全丢）
  完全由这一条引起：texrender 的纹理由 `begin` 现建，之前 `get_texture()` 返回 NULL，
  任何「用 texture 判空决定能不能渲染」的写法都会把好目标误判成坏目标。后续 5b/5c
  挑目标时必须按 **texrender 对象**比较。
- **新增风险：effect 参数是一次性的。** `gs_technique_begin_pass()` 提交后会消耗该值，
  同一批参数不能连画五趟；`3517 : 1539 ≈ 4 : 3` 的比例就是「几趟没绑」的证据。
  3.1.54 改为每趟 draw 前重绑，警告归零。以后新增多 technique 着色器必须照此办理。
