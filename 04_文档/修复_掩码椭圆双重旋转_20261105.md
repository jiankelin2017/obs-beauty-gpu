# 修复：掩码椭圆被旋转了两次（歪头时美白范围变大）

> 日期：2026-11-05
> 影响面：CPU `buildMaskInto` 与 GPU `mask.hlsl` 两条掩码路径（同一个 `faceGeom`）
> 触发条件：**歪头**（`|θ| > 2°`），正脸不受影响
> 验证：离线回归台 4 条用例重采基准后全绿；15° 倾斜帧掩码覆盖率 7.82% → 7.47%

## 症状

用户能感觉到的只有一句：「歪着头比正着脸，**美白**范围铺得更开。」没有报错、没有崩溃，日志里掩码覆盖率也"看着正常"，所以一直没被当成 BUG。

## 根因

`beauty_core.cpp` 里算掩码几何时，把**同一个旋转套了两遍**：

```cpp
// 旧代码
const float ac = fabsf(rc), as = fabsf(rs);
const float lw = rolled ? (sf.w * ac + sf.h * as) : sf.w;   // ← 已经是旋转后的 AABB
const float lh = rolled ? (sf.w * as + sf.h * ac) : sf.h;
const float hw = lw * kFaceBoxGrow * 0.5f;                   // ← 却被当成"局部半轴"
const float hh = lh * kFaceBoxGrow * 0.5f;
const float hx = hw * ac + hh * as;                          // ← 又转一次去算包围盒
const float hy = hw * as + hh * ac;
```

`hw/hh` 往下有两个用途，其中**椭圆半轴**这一路要求的是"脸自身轴上的半宽/半高"：

- CPU 椭圆距离场 `q = sqrt((u/a)² + (v/b)²)`（`a = hw, b = hh`，`u/v` 已转回局部系）
- GPU `faceGeom = (cx, cy, a=hw, b=hh)`，`mask.hlsl:192` 同样按局部系算

喂进去的却是 AABB 半宽，于是椭圆沿旋转方向被撑大。放大倍数是 `|cosθ| + |sinθ|` 再乘一次自己：

| 倾角 θ | 半轴放大 | 掩码面积 |
|---|---|---|
| 0° | 1.00× | 不变 |
| 5° | 1.09× | +18% |
| 15° | **1.50×** | +125% |
| 45° | 2.00× | +300% |

同一条错误还带歪了三处：羽化宽度 `fe`（用 `lw`）、脖子半宽/长度（`neckA_/neckB_` 用 `lw/lh`）、脖子矩形起点（`cy + hh`）。也就是说歪头时**脖子那一截也一起变宽变长**。

## 为什么"看得见"的是美白边界，不是磨皮边界

同一份掩码（`mask_`）被磨皮、美白、清晰、五官、美形五段共用，但**只有美白会把掩码边界直接画在脸上**：

- 美白是"按掩码插值一个色温/亮度偏移"，边界处偏移量突变 → 一条可见的色界。掩码大一倍，这条色界就外移一倍。
- 磨皮是双边滤波 + 掩码加权混合，权重从 1 渐变到 0 的过程本身就有几十像素过渡，边界外扩 1.5 倍在观感上被渐变吸收，很难看出"边界变了"。
- 清晰/五官/美形同理，作用域本来就小，边界落在五官内部，不外露。

所以验收口径要定在**美白边界**：歪头到 15°~30° 时，颧骨外侧/下颌线外侧那条"肤色更亮"的分界应当基本贴合脸型，而不是随倾角外扩。这条已写进本轮的验收说明。

## 改法

三组量各归各位，一个 `const` 改完，没有分支：

```cpp
const float lw = sf.w, lh = sf.h;                            // 脸自身轴上的宽高
const float hw = lw * kFaceBoxGrow * 0.5f, hh = lh * kFaceBoxGrow * 0.5f;  // 椭圆半轴
const float hx = hw * ac + hh * as, hy = hw * as + hh * ac;   // 只用于像素迭代的 AABB
```

`θ = 0` 时三者退化成旧值；`θ ≠ 0` 时半轴回到"脸真的有多宽"。

## 验证

1. **静态帧**：黄金基准 4 条（blur100 / mixed / sharp / region）在改前全绿；改后全部有差异 —— 因为基准帧本身带 ≈1.4° 的检测滚转角，`(ac+as)² ≈ 1.05`。差异集中在掩码边界（10910 px ≈ 1.18%，maxdiff 7）。**确认是有意变化后重采基准**，重采后再跑全绿（旧基准备份为 `goldens/*.raw.2.17.2bak`）。
2. **倾斜帧**：把基准帧旋转 15° 得到 `_rot15.raw`，同一参数跑：

   | | 掩码像素 | 占比 |
   |---|---|---|
   | 改前 | 72092 | 7.82% |
   | 改后 | 68843 | 7.47% |

   缩掉的 4.5% 正好是"第二次旋转"多出来的那一圈。
3. **推理链无影响**：这次只动几何，`BEAUTY_SEG_MIX=0` 时分割纹理一个字节都没变。
4. **人工验收（待做）**：开 OBS、美白拉到能看清边界，头从正立缓慢歪到 30°，看**美白边界**是否跟着脸走而不是向外扩。磨皮不作为判据（渐变会盖掉差异）。

## 顺带修掉的第二个旧 BUG：离线回归台编译不起来

`06_离线验证/build_offline.ps1` 的源文件清单里**没有 `beauty_skinseg.cpp`**。P0 把 `skinsegRun/skinsegEnabled` 接进 `beauty_core.cpp` 之后，`core_probe.dll` 一直链接失败：

```
beauty_core.obj : error LNK2019: 无法解析的外部符号 skinsegEnabled / skinsegRun
```

也就是说：**从 P0 落地那一刻起，这道"改代码前先跑离线回归"的门禁就是坏的**，只是没人重跑过。已把 `beauty_skinseg.cpp` 加进清单，现在 `build_offline.ps1` → `offline_regress.py check` 可以正常跑。

## 没动的两处（有理由）

- `emaMaskFace` 的 8% / 15% snap 阈值：看下来是设计取舍（大跳直接采纳，避免换人拖影），不是缺陷。唯一可挑的是 y 方向位移也用 `sf.w` 当分母，属于量纲不讲究，不产生可见后果。
- `g_skinAdaptEma = 1.0`（肤色中心不平滑）：代码里写明了理由 —— 任何 <1 的系数都会让同一张图重复处理得到不同掩码，破坏确定性对拍。属于刻意选择。
