## 0. 一句话

现在每帧有 **5~7 ms 是纯搬运**，只为把像素送到 CPU 上算一张 8-bit 掩码、再传回 GPU：
4K 的 **掩码上传 2.05 + 对齐整帧上传 ≈3.0**（2a 能省），以及 **下载 4.57 + 送检测 worker 的整帧 memcpy 2.58**（2b 才省）。
5b-2a 把掩码改在 **GPU 上直接从源纹理算**，目标是 4K **13.6 → 约 9 ms**、720p **2.0 → 约 1.6 ms**，
且 **掩码逐像素 `maxdiff ≤ 1`**（与 5c 同一条判据线）。
再往下的 2b 能到 **约 1.9 / 0.45 ms**，但**不再逐字节等价**（见 §6）。

## 1. 今天的实测底座（3.1.63 同会话 A/B，`out` 臂 = 生产默认）

| 项 | 720p | 4K | 说明 |
|---|---|---|---|
| 往返 | **2.03** | **13.64** | 已有 5b-1 |
| ├ 下载 | 1.01 | 4.57 | `stagesurface map` + memcpy 到 `buf_in`，**含 GPU 同步等待** |
| └ 引擎 | 1.01 | 9.12 | CPU 像素算力 |
| 　├ 掩码 | 0.28 | 2.58 | **送检测 worker 的整帧 memcpy**（异步路径下 `buildMaskInto` 跑在 worker 上，**不在这段计时里**；比值 9.2 ≈ 像素比 9.0，自洽） |
| 　└ 磨皮段 | 0.61 | 6.51 | 其中 `prep` 0.39 / **5.08** |
| 　　├ 对齐整帧上传 | 0.22 | ≈3.0 | `prep` 里的帧上传（4K 对齐率 ~100%，几乎每帧都传） |
| 　　└ 掩码两张 R8 上传 | 0.17 | 2.05 | `skin_tex` / `eye_tex` |

**结论：4K 的 12.2 ms 分两组，2a 只能吃第一组。**

| 组 | 明细 | 4K | 720p | 谁移除 |
|---|---|---|---|---|
| A. 掩码产物回传 | 掩码上传 2.05 + 对齐整帧上传 3.0 | **5.05** | 0.39 | **2a** |
| B. 把像素送给 CPU 检测 | 下载 4.57 + 送 worker 的 memcpy 2.58 | **7.15** | 1.29 | **2b（非等价，见 §6）** |

> 这一条是复核时改掉的旧口径：`掩码` 那 2.58 ms 曾被当成「在 CPU 上建掩码」，其实异步路径下
> 建掩码在 worker 线程，这段计时只是 `submitAsync` 的整帧 memcpy。**算错 4 ms，就会把 2a 的
> 预期从 8.6 写成 6.0。**

## 3. 为什么不能「只把像素循环换成着色器」

顺序上有个死结，必须先解开：

```
今天的顺序： process(src) → updateMask(src) [检测+建掩码] → 算 flags/job.warp → 问钩子 claim → 跑各段
```

- `job.warp`（5c 的逐脸几何）**必须由检测结果算**，而检测要吃像素；
- 想省掉「下载」，就得在**没下载之前**知道这帧会不会全认领 —— 但 flags 又在检测之后才定。

**两种解法：**

1. **钩子提前 + 宿主自证**（推荐）：宿主本来就掌握面板参数，可以先给一个「预测 claim」；
   引擎按预测 claim 决定「要不要喂 CPU 像素」。预测错的代价只是回退（多一帧慢），不会算错。
2. **双阶段**：引擎先只跑检测（用小图），把 faces 交出去，宿主算完几何再决定下载与否。
   干净但改动大，且检测本身也要像素。

→ 本文按 **方案 1** 写：**claim 预测失败 = 回退 CPU**，与今天所有钩子的契约一致（「只会变慢，不会变错」）。

## 4. 目标架构

```
           ┌─ 宿主 ──────────────────────────────────────────────┐
in_tex ────┤ mask.hlsl（全帧 R8 ×2：skin / eye）                   │
           │   ↑ 每张脸的 uniform：cx,cy,hw,hh,feather,neck 模式    │
           │   ↑ 肤色椭圆中心（CPU 给，estimateSkinCenter）          │
           ├──────────────────────────────────────────────────────┤
           │ 链：磨皮 → 色调 → 细节 → 美形（都直接采样这两张 R8）    │
           └──────────────────────────────────────────────────────┘
                        │ 仅在「本帧有 CPU 段要跑」时
                        ▼
                 buf_in（下载）+ CPU buildMaskInto（今天的路径，一字不改）
```

新增三样东西：

1. **`shaders/mask.hlsl`**：1 technique / 1~2 入口，输出 `skinMask`（R8）与 `eyeMask`（R8）。
   输入：源纹理、`texel`、每脸常量（最多 8 张，与 5c 同上限）、肤色椭圆（cb/cr/ru/rv）、
   `maskShape` 位（1=椭圆 / 4=脖子逐行 / 2=脖子椭圆）、`noFace` 语义。
2. **引擎侧「外部掩码」注入**：`beautyCoreSetMaskProvider()` —— 引擎在 `updateMask` 里
   **优先问宿主要掩码**，宿主给不出（或本帧要跑 CPU 段）才走今天的 `buildMaskInto`。
   这是**唯一必须改引擎的地方**，且是 additive：不设 provider 时行为逐字节不变。
3. **宿主 claim 预测**：`beauty_chain_hook` 之前先跑一次「参数预测」，决定是否下载整帧。

## 5. 等价性策略：四层门禁（一个门禁只断言一件事）

| # | 门禁 | 判据 | 抓什么 |
|---|---|---|---|
| M1 | **掩码对拍**（新） | 同一帧、同一组 faces，GPU 掩码 vs CPU `buildMaskInto`：`maxdiff ≤ 1`（8-bit），并单独计数「ROI 外差异」（必须 0） | 像素公式/取整/边界 |
| M2 | 既有磨皮对拍 | `maxdiff ≤ 1`、改动量 gpu≈cpu | 掩码 → 磨皮的整链 |
| M3 | 既有细节对拍 | `maxdiff ≤ 1` | 掩码 + `noMask` 语义（E6） |
| M4 | 5b-1 绘制对拍 | `RGB maxdiff = 0` | 直绘路径没被碰坏 |

**M1 是这次唯一的新门禁，也是唯一能抓「公式抄错」的那条**（T1 的 `.b=0` 就是这么抓到的）。
它必须**逐像素比整张掩码**，不能只比覆盖率（覆盖率相同但边界偏移 3 px 的错法完全可能）。

> ⚠ 别把「掩码对不对」和「磨皮对不对」塞进同一个 `maxdiff`（3.1.59 的教训）。

## 6. 分档落地

### 5b-2a（必做，可独立验收）

- `mask.hlsl` + 引擎 provider + 宿主预测 claim；
- 全认领帧：掩码 GPU 建、**不再上传掩码两张 R8**、不做 heldFrame 对齐；
  **整帧仍然下载**（检测要吃像素，见 R4），CPU 侧只做检测与 ROI/统计；
- 有 CPU 段（五官 / 预测失败 / 着色器缺失）：**整帧回退到今天的路径**，逐字节不变。

预期（4K）：省 A 组 `掩码传 2.05 + 对齐整帧上传 3.0` ≈ **5.05 ms**，加回 GPU 掩码 pass 约 0.2~0.3 →
**13.64 变约 8.6~8.9 ms**；720p：省 0.17 + 0.22 ≈ 0.39 → **2.03 变约 1.6~1.7 ms**。
验收：M1（≤1）+ M2/M3/M4 全过；`下载` 与 `掩码`（sent-to-worker memcpy）两项**不变**
—— **这是 2a 的天花板，别指望它把 4K 做到 1.5 ms**（见 R4）。

### 5b-2b（可选，需要你先拍板）

把「检测输入」也改小：GPU 缩到 640×360 再回读（4K 33 MB → 1.6 MB），`下载 4.57 → ~0.25`、
送 worker 的 memcpy `2.58 → ~0.2`。**4K 8.6 → 约 1.9 ms、720p 1.6 → 约 0.45 ms。**

**代价：这条不再逐字节等价。** 检测器内部会再缩一次（320/640），两次重采样 ≠ 一次，
人脸框可能差 1~2 px，掩码边界就跟着差。**这一档只能用「统计等价 + 79.0 分不降」来验收**，
不能用 M1 的 ≤1。要不要做，是个产品决策，不是技术问题。

### 5b-2c（收尾）

`updateMotion` 改 GPU 归约 + 16 float 回读（细节段需要 `beta`，差值会直接改细节强度）。
只在 2a/2b 之后做，且必须过 M3。

> **2026-11-04 注（分清两个「motion」）**：前置条件 2a/2b 早已满足（2a = 掩码上 GPU 的 2.6.0，
> 2b = 检测输入缩小 = S4b 2.7.0，见 §5b-2b），但**本项本身仍未做** —— 它要的是**细节段 `beta`
> 的归约**，会改画面强度。
> 2.11.0 的「方案C」把**另一个** motion（S7 的 16×16 亮度运动网格，只决定「多久检测一次」）
> 搬到了 GPU，用 64×64 小图算、`maxdiff=0`，**与本节无关**，不要拿它当 5b-2c 已完成。
> 两者的区别：本节改「细节多强」，方案C 只改「检测多勤」。

## 7. 风险与开放问题

**R1 脖子逐行扫描（最大风险）**。`buildMaskInto` 的 `g_maskShape & 4` 分支是**逐行顺序扫描**：
从中心向两侧走，连续 3 个非肤色像素算到头，太窄就退回固定半宽（`beauty_core.cpp:2487`）。
GPU 上没有顺序语义，三条路：
  a. 逐行前缀和（log-step scan），完全等价但要多 2 个 pass；
  b. 固定窗口 ±maxHalf 内找「最外侧的肤色点」，再按 gap 规则判连续 —— **不完全等价**；
  c. 脖子仍留 CPU（只这一小段，行数 ≈ 0.45×脸高，几百行），用**脸框 ROI 的小图**算。
→ 建议先做 **c**（最省事、最安全）；若 2a 的收益已达标，再考虑 a 提性能。

**R2 取整**。CPU：`(int)(m*255+0.5)`、羽化 `(int)(t*t*(3-2t)*256+0.5)`、落笔 `(wgt*feather+128)/256`，
全是「先乘后加 0.5 再截断」。HLSL 里必须用 `floor(x+0.5)` 显式写出，**不能依赖隐式 round**（它到偶数）。

**R3 对齐语义**。今天 `对齐` 是「掩码来自上一帧 → 拿上一帧的像素来配它」。
GPU 掩码是从**本帧纹理**算的，天然同源 → 对齐退化成 no-op。
这不是 bug，但**会改掉 1 帧延迟**：观感上更实时，输出与 CPU 基准不再逐帧对齐。
→ 必须在**回退帧**保留 heldFrame 路径，并把 `对齐` 统计改名为「掩码来源」，
否则这个指标会永远显示 100% 而失去意义（T7 刚踩过「指标含义变了但没人注意」的坑）。

**R4 检测仍要像素**。2a 之后 `下载` 一分不少（4K 4.57 ms）。**这是 2a 的天花板**，
写清楚，别指望 2a 能把 4K 做到 1.5 ms。

**R5 五官（REGION）**。五官段没有 GPU 版，一旦开启就整帧回退 —— 5b-2a 对五官用户零收益，
与 5c 的边界完全一样（段顺序决定）。文档和日志都要写明。

**R6 protect 语义**。`eyeMask` 在 `noMask` 时是**全 0**（E6：detailRefill 把无掩码当 0，磨皮当 255）。
GPU 侧两个 shader 的 `noMask` 分支必须照抄，不能合并。

**R7 纹理格式**。R8 当渲染目标在 D3D11 上没问题，但 OBS 的 `gs_texrender` 默认参数要显式指定
`GS_R8`；且 `mask.hlsl` 输出必须 `nointerpolation`/point 采样，避免 OpenGL 后端插值（OBS 允许 GL）。

**R8 8 张脸上限**。常量缓冲按 8 张脸预留（与 `BEAUTY_WARP_MAX_FACES` 一致）；
超过 8 张一律回退 CPU（与 5c 同策略，宁可慢不可错）。

**R9 ROI 与统计的语义会变（容易漏）**。今天的 `bounds_` 是**落笔后**的包围盒（`buildMaskInto`
边画边统计，`:2325`），GPU 版拿不到这个「实际画了多少」，只能退化为「脸框 ∪ 脖子几何 + pad」。
两者通常只差几个像素，**但 ROI 是磨皮 band 与细节段的输入**：
  · 变大 → 多算像素，结果应当不变（`pad ≥ radius` 的规则已经保证边界邻域完整）；
  · 变小 → **结果会变**，这是必须避免的方向。
所以 R9 的验收就是 **M2/M3**：如果 GPU 侧的 ROI 与 CPU 侧不一致导致输出变了，`maxdiff` 会立刻报。
同时 `掩码%` 这个诊断指标的含义要从「落笔像素占比」改成「几何面积占比」—— **必须改名或标注**，
否则又是一次「指标含义变了没人注意」（T7 的教训）。

## 8. 验收标准（做完怎么算过）

1. `verify_mask_compiles.py`：静态门禁（OBS 方言五条红线 + fxc 编译），**新增任何方言写法必须补一条检查**；
2. M1 掩码对拍：720p / 4K 各一次，`maxdiff ≤ 1`、ROI 外差异 0；
3. M2/M3/M4 全绿；
4. 4K 往返 ≤ 9 ms（2a）、720p ≤ 1.7 ms（2a）；数字按同会话 A/B 取中位；
5. `BEAUTY_GPU_MASK=0` 一键回到今天的路径，且**逐字节相同**（回退开关是硬要求）。

## 9. 明确不做

- 不做「掩码降分辨率」：磨皮/细节都按全分辨率采样掩码，降采样会改边界（另立项）。
- 不动检测模型与输入尺寸（那是 79.0 分的根，R4/2b 才碰）。
- 不合并磨皮与掩码 pass：`draw` 只量提交时间，合并毫无收益（4K 线性度结论）。

> 4 个 bug**，其中 3 个是「几何/参数取错时刻」这类问题 —— 如果先接 provider 再验，这四个 bug 会以

**切片 1 的边界**（写死在 shader 文件头，不要当成遗漏）：

- **只支持 1 张脸**；多脸时宿主整帧回退 CPU。理由是 OBS 的 `blend_op = max` 字符串支持
  在本机没有源码可查（`参考文件\03_依赖与SDK_OBS` 只有头文件与库），不冒险；等切片 2 用
  「ping-pong + max(prev, new)」或验证过 blend 之后再扩。
- 支持 `maskShape` 的 bit0 / bit1（脸/脖子的椭圆变体），**不支持 bit2**（脖子逐行跟肤色扫描，
  是顺序语义）；宿主见到 bit2 就回退。
- 不做 `noMask` 语义：无脸时宿主绑常量纹理，与 3.1.51 的既有行为一致。

**门禁自证**（沿用 T1 的做法，证明它不是空转）：三组变异各被对应项抓住并退出 1 ——
`0.587→0.588` 被 `[I]` 抓、`>>8 → /256` 被 `[L]` 抓、删掉过曝门控被 `[J]` 抓。

**切片 1 抓到的两个坑（留给切片 2 的提醒）**：

1. **门禁自己会误报**。`[I]` 最初用字面量 `"-0.331264"` 匹配，而 shader 里写的是
   `- 0.331264`（二元减号），于是健康代码被判红。改成**整条表达式**匹配
   （`cb = -0.168736*c.r - 0.331264*c.g + 0.5*c.b`）后，既不误报，也比字面量更严
   —— 连符号和顺序一起钉死。
2. **脖子椭圆的循环上下界随模式变，这是宿主契约，静态门禁抓不到**。
   矩形分支 y ∈ [y1, …)，椭圆分支 y ∈ [clamp(cyN−B), clamp(cyN+B))（会伸进脸框区域）。
   如果两条共用同一个 `ny0`，椭圆上半截被切掉、脖子掩码少一块，**编译照过、画面只是略变**。
   → 结论：`neckRect` 的 y 对按**模式**填，写进 shader 文件头；这条只有 M1 能验。
