# 修复：五官立体拉满时出现四个白圈（2026-11-05）

## 1. 现象

用户报：**「五官立体」滑块拉高后，明显看到四个白圈，分别在额头、下巴、两侧脸颊。**

差分场（拉满 vs 关闭，放大 8 倍）能直接数出来：额头一个大椭圆、左右各一个圆盘、
下巴一个小圆盘，边界清晰可辨 —— 与用户描述完全一致。

## 2. 根因：羽化语义是「平台半径」，不是「软边宽度」

`beauty_region.cpp` 的椭圆求值：

```cpp
const float fall = 1.0f - smoothStep(e.feather, 1.0f, d);   // d = 归一化椭圆距离
```

`feather` 被当成**平台半径**：`d < feather` 的内圈恒为满增益，只有外圈
`feather → 1` 才往下落。3.1.23 拟合出来的亮部值是 **0.705** ——
也就是说 70% 半径内亮度是一个常数，剩下的 29.5% 才过渡。

于是每个椭圆都是一个「平顶圆盘」：

- 平顶内部亮度恒定，人眼没有梯度可看；
- 平台与斜坡的交界处一阶导数连续、**二阶导数不连续**（曲率突变）；
- 视觉系统对曲率突变的响应就是**马赫带** —— 看到的是一道亮圈/暗箍，
  哪怕灰阶差只有 8~12。

这不是强度问题：把滑块调小只会让圈变淡，调到某个值以下才「看不见」。
用户感觉「拉高才明显」正是因为幅度越大，马赫带越强。

第二个原因：8 个椭圆**彼此不重叠**，各自是孤立斑点。斑点越小、越圆，
越像「打在脸上的手电筒光斑」，而不是「脸有立体感」。

## 3. 改法

### 3.1 给椭圆加一个形状开关 `dome`

`Ellipse` 结构新增 `float dome`（`beauty_region.h`）：

| dome | 求值 | 用途 |
|---|---|---|
| 0 | `1 - smoothStep(feather, 1, d)` | 旧行为，其它几族（亮眼 / 眼袋 / 法令纹）保持不动 |
| >0 | `(1 - smoothStep(0, 1, d))^dome` | 钟形：中心 1、边缘 0，**两端导数为 0，没有平台拐点** |

没有引入新的 uniform：GPU 侧参数纹理每椭圆 3 个 texel，第三个 texel 原本
`C=(shade,_,_,_)` 有两个空位，`dome` 放进 `C.y`，`obs-beauty.cpp` 上传、
`region.hlsl` 读取，CPU/GPU 逐字对应。

### 3.2 亮部改成互相重叠的连续光场

保持 8 个解剖锚点（额 / 眉弓 / 鼻梁 / 左右颧 / 上唇 / 下巴 / 下颌），
但把亮部椭圆放大到**互相重叠**，重叠区的平台被邻居填平，边界自然消失：

| 项 | 旧 (rx, ry, gain) | 新 |
|---|---|---|
| 额头 | 0.350, 0.115, +8.53 | 0.470, 0.200, **+9.30** |
| 眉弓/眼窝 | 0.3525, 0.145, −2.15 | 0.340, 0.115, **−4.65** |
| 鼻梁 | 0.050, 0.180, +6.90 | 0.090, 0.245, +6.90 |
| 左颧 | 0.1525, 0.100, +7.65 | 0.235, 0.150 (rot −0.14), **+7.35** |
| 右颧 | 0.150, 0.1125, +10.64 | 0.235, 0.150 (rot +0.14), **+7.35** |
| 上唇 | 0.290, 0.0925, −7.25 | 0.265, 0.080, **−7.80** |
| 下巴 | 0.110, 0.070, +9.65 | 0.160, 0.100, **+9.60** |
| 下颌/脖 | 0.5075, 0.190, −4.80 | 0.505, 0.185, **−6.30** |

增益整体 ×1.5 是为了补回「钟形没有平台」丢掉的面积（钟形面积均值 1/3，
旧的平顶 0.75），保证观感总量不掉。旋转符号按解剖：屏幕左侧那条朝左下，
右侧朝右下。

## 4. 效果量化

`frame_1280x720`（脸宽 207 px），亮满 100 档，只开这一项：

| 指标 | 旧 | 新 |
|---|---|---|
| 脸内 dY 均值 | +0.672 | **+0.677**（总量不变）|
| dY p95 | 7.60 | 5.59 |
| 峰值 | +12.2 / −6.7 | +8.6 / −6.2 |
| **max\|∇²Δ\|**（「看得见圈」的直接来源）| **1.887** | **0.126**（降 15 倍）|
| max\|∇Δ\| | 2.599 | 0.654 |

实拍 720p 大脸（`face_front_720p`，脸宽 331 px）：峰 +12.3/−7.1 → +8.9/−6.1，
∇² 0.90 → 0.42。

> 说明：总量（脸内均值、p95）保住了，但**峰值降了约 30%**。
> 峰值是「椭圆正中心那几个像素」，旧版是一大片满增益；新版是连续场。
> 如果用户觉得立体感不够，先调 `BEAUTY_REG_THREED=1.2` 看，再决定要不要动表。

## 5. 验证

1. **CPU == 离线模拟器**：`sim_regions.py`（逐式重放）对新导出的椭圆表输出与
   引擎逐字节相同（maxdiff=0）。说明 dome 的 C++ 实现与设计公式一致。
2. **GPU == CPU（插件自带对拍）**：`BEAUTY_REGION_CMP=1` 在 1920x1080
   `blur=30 + threed=100` 下 `maxdiff=1、差异像素 1 个`，判定通过
   （对比对象是同一份几何重建出的 CPU 参考，`ellipses=8+0+0`）。
3. **黄金基准**：`blur100 / mixed / sharp` 逐字节不变（maxdiff=0）；
   `region`（含 threed 30）按预期变化，已重采并复跑 4/4 绿。
4. **自检**：`offline_regress.py selftest` 确定性与零参数直通都逐字节相同。
5. **fxc**：`PS_Region` 单独编译通过。

### 5.1 测试台踩到的坑（不是本改动引入，但会误导验证）

用「静态图源 + obs-websocket 截图」做 GPU 对拍时，**截出来的图像完全没有立体效果**：

- `GetSourceScreenshot(源)` 只有在**该源是当前节目场景里一个启用的场景项**时才
  经过滤镜；否则返回的是原图（0 像素变化）。
- 走 GPU 掩码链（`geomOnly`）时，静态图源那几帧的 mask 纹理是空的 →
  `PS_Region` 里 `mw = 0` 直接返回原值，效果整个消失。
  同一次运行里加 `BEAUTY_GPU_MASK=0`（改回 CPU 掩码 + 上传）就对拍通过。
  实拍摄像头每帧都有新鲜几何，不会走到这个状态，所以线上看不到。

结论：这类验证要么用**摄像头实拍**，要么加 `BEAUTY_GPU_MASK=0`。
