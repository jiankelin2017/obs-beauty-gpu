# Phase 0 — 基线测量规程（只读，不碰代码）

**目标**：用现有 CPU 版的 `BEAUTY_PROFILE=1` 计时，量出 **下载 / 引擎 / 上传** 三项在
720p / 1080p / 4K 下的真实 ms/帧。这是「值不值得做 GPU 化」和「做完省多少」的**硬证据**，
也是后面每个 Phase 验收时对比的基线。

---

## 一、要测的三项分别是什么

来自 `obs-beauty.cpp` 的每帧管线与计时块：

| 项 | 代码位置 | 含义 | GPU 化后 |
|---|---|---|---|
| **下载** `prof_dl` | L642–668 | `gs_stage_texture` + `gs_stagesurface_map`（同步等待）+ `memcpy` 把整帧 GPU→CPU | **消失**（画面不再下 CPU） |
| **引擎** `prof_proc` | L670–703 | `beautyEngine().process(slot, buf_in, buf_out, …)` —— 纯 CPU 像素运算（磨皮/美白/美型/清晰/红润/细节回填），GPU Phase 2–5 要吃的就是它 | **消失**（改走着色器） |
| **上传** `prof_up` | L705–736 | alpha 透明化 + `gs_texture_set_image(out_tex, …)` 把结果回 GPU + 绘制 | **消失**（结果本就在 GPU） |

> 结论：**三项之和就是 GPU 化要消灭的整笔往返**。其中「引擎」是纯 CPU 算力（降功耗的核心），
> 「下载/上传」是 GPU↔CPU 拷贝与同步等待。

## 二、测量步骤（在你机器上跑）

1. **准备场景**：OBS 里加一个「美颜」滤镜到某个视频源（摄像头或一段视频）。
2. **设代表参数**（别用全 0，全 0 会 `skip_sdk` 直通，引擎项=0，量不出东西）：
   - 磨皮 60、美白 40、红润 20、清晰 30、大眼 10、瘦脸 10、下巴 10（中高负载，贴近真实使用）。
3. **开计时**：启动 OBS 前设环境变量
   ```
   set BEAUTY_PROFILE=1
   ```
   （或在 OBS 快捷方式里加这个环境变量；mac/Linux 用 `export BEAUTY_PROFILE=1`）。
4. **跑 3 种分辨率**各 ≥30 秒（让 180 帧窗口至少刷新一次）：720p(1280×720)、1080p(1920×1080)、4K(3840×2160)。

> ⚠ **实测踩到的坑（2026-10-31）**：三档不一定都能在摄像头上跑。
> 本机 Integrated Camera 只支持 1280×720，请求 1920×1080 时 dshow 直接
> `Video format match failed`，源起不来、滤镜一帧都不跑。
> 拿不到的分辨率改用"等像素"办法：把滤镜挪到**场景源**上，用场景的
> `custom_size`（`cx`/`cy`，见 `obs-scene.c:1281`）把滤镜工作尺寸顶到目标分辨率，
> 摄像头画面被缩放填满。像素量一致，但画面内容是放大过的，必须在文档里标注。
> 用 `05_验证/phase0_prep.py --mode scene --canvas 3840x2160` 一键生成。
>
> ⚠ **3.1.50 补的第二个坑：跨分辨率对比必须单变量。** `phase0_prep.py` 的默认参数是
> 本规程第二节的「代表性负载」（磨皮 60 + 美白 40 + 红润 20 + 清晰 30 + 美形三项 10），
> 而单分辨率窗口（如 720p `blur_level=100` 其余全 0）用的是另一套值。直接横比
> `磨皮` 分项，差的是「分辨率 **和** 强度」两件事，结论必错。
> 要量线性度请加 `--only-blur 100`（面板参数全清零、只留磨皮），保证只有一个变量。
>
> 4K 档配套用 `03_装机/4_run_4k.bat` 启动（它只多传一个 `-Collection phase0_baseline`），
> 这样 720p 的 `beauty_test` 集合不会被覆盖。
>
> 另一条同类坑：集合 JSON 里的 `resolution` 字段**不管用**，OBS 的画布来自 profile 的
> `basic.ini`（`BaseCX/BaseCY`）；要改场景工作尺寸只能走 `custom_size`。
5. **取日志**：OBS 日志在 `%AppData%\obs-studio\logs\` 下最新一个 `.txt`。
   搜关键词 `性能 `（带空格）即可定位 `性能 WxH：下载 X + 引擎 Y + 上传 Z = T ms/帧` 行。

## 三、自动汇总（脚本）

把日志交给解析脚本，自动按分辨率聚合并算「GPU 化可消除总量」：

```
python 05_验证/phase0_parse_log.py "路径\to\obs64-2026-xx-xx-xxxxxx.txt"
```

脚本输出每张分辨率的：样本数、三项均值、往返总量 T，以及「若全上 GPU，每帧省 T ms」
（≈ 引擎 + 下载 + 上传）。

插件 **3.1.44** 起，性能行多了两项，脚本会自动解析成两列：

```
性能 1920x1080：下载 2.26 + 引擎 21.30 + 上传 1.24 = 24.82 ms/帧（180 帧平均）掩码 21.30% 有脸 100% 对齐 180/180（100%）
                                                                        ^^^^^^^^^^^^  ^^^^^^^^^^
```

- `掩码 %` = 本窗口平均「皮肤掩码置位像素 / 全帧像素」。**这是解释引擎耗时差异的第一变量。**
- `有脸 %` = 本窗口里检出人脸的帧占比。美形三项（大眼/瘦脸/下巴）只在有脸+有关键点时才算，
  所以这一项直接决定该窗口的总耗时。

> ⚠ **判读铁律**：比较两个窗口的 ms 之前，先看 `掩码% / 有脸%` 是否接近。
> 覆盖差一倍，ms 就能差 2.3 倍（见第五节结论 4）—— 那是画面变了，不是代码变快了。
> 旧日志（3.1.43 及以前）没有这两项，脚本对应列显示 `-`。

插件 **3.1.48** 起，性能行末尾再多一项 `边框 Z%`：

```
... 对齐 120/120（100%）边框 31.4%
```

- `边框 %` = 本帧磨皮 ROI 包围盒（人脸框并集）面积 / 整帧面积，窗口内取均值。
- **它和耗时没有关系**，因为 `surface3RgbBand` 目前收了 `roi` 形参却从不使用，
  包围盒大小不影响计算量。它回答的是另一个问题：**「让 ROI 真正生效」最多能省多少**。
- 判读：`边框 30%` 左右 → ROI 裁剪理论可省约 70% 磨皮时间；`边框 70%` 以上 → 最多省 30%，
  不如直接做 GPU 翻转。这个数是**上限**，盒式滤波还要向外扩核半径，实际略低。
- 无包围盒的窗口打 `边框 --`，**不计入平均值的分母**——若当成 0% 计入，会显示成
  「包围盒极小、ROI 收益极大」，与「这一帧压根没有包围盒」导出相反的结论。
- 与 `掩码%` 不是一回事：包围盒是矩形，掩码是皮肤像素，前者通常是后者的 2~3 倍。

插件 **3.1.49 ~ 3.1.52** 起，分项行（`seg 分项 …`）末尾陆续追加四个 ASCII 锚点。
它们都是**追加在行尾**的，既有正则不需要改。判读表：

| 锚点 | 版本 | 含义 | 判读 |
|---|---|---|---|
| `gpusm=命中/调用(占比)` | 3.1.49 | **单段钩子**（只接管磨皮）的接管率 | 低于 100% = 有帧回退（着色器缺失 / map 失败） |
| `sm=提交/回读/拷贝(n=N)` | 3.1.50 | 磨皮段三段细分（毫秒） | `提交` 只量 draw 命令提交，不是 GPU 计算时间 |
| `prep=准备/掩码` | 3.1.51 | 钩子准备段：整帧上传 + 掩码上传 | 「钩子外」应趋近 0 |
| `chain=命中/询问` + `S/T/R/D/W` | 3.1.52 | **段区间钩子**的命中率与五段认领分布 | **3.1.54 实测形态**：`S/T/R/D/W=180/0/0/180/0`（该用例色调/美形全 0，所以 T/R/W = 0 属正常）。**判据是 `D` 位必须等于命中数**；`chain` 满格而 `D=0` 正是 3.1.52「细节段从未接管」的翻车形态 |

> ⚠ **3.1.52 起 `sm=` 的「回读」含义变了**：chain 生效时它等的是**整条链**
> （磨皮+色调+细节）的 GPU 时间，不再只是磨皮回读。**不要拿 3.1.52 的 `sm=`
> 直接与 3.1.51 比** —— 要判断收益，看 `seg` 里的「细节」项是否归零、引擎总耗时是否下降。

**3.1.54 两趟实测样本（720p 一行原文 + 4K 中位数示意，可直接当格式与判据对照）：**

```
seg 分项 1280x720：掩码 0.30 + 磨皮 2.27 + 色调 0.00 + 五官 0.00 + 细节 0.00 + 美形 0.00 = 2.57 ms（引擎 2.57，差 0.00） chain=180/180 S/T/R/D/W=180/0/0/180/0 sm=0.04/1.28/0.31(n=180) prep=0.48/0.19 ch=0.00/0.02
seg 分项 3840x2160：掩码 2.73 + 磨皮 18.50 + 色调 0.00 + 五官 0.00 + 细节 0.00 + 美形 0.00 = 21.16 ms（引擎 21.16） chain=180/180 S/T/R/D/W=180/0/0/180/0 sm=0.07/8.87/3.27(n=180) prep=5.22/2.16 ch=0.00/0.03
```

> 4K 那行是 **158 个窗口各分项中位数拼成的示意值**，不是某一帧的原始行
> （原始行逐窗口波动，整帧 24.48~39.07 ms）。真实原文见日志
> `2026-10-31 19-45-28.txt`。该日志已定稿（`obs64` 退出后复跑确认）。

两行相除即得缩放比（`05_验证/analyze_4k_ratio.py` 自动做）：**`draw` 1.75×，
`map` 6.93× / `copy` 10.55× / `prep` 10.88× / `掩码` 9.10× / `上传` 10.96×
随像素增长；`下载` 5.23× 是唯一明显亚线性的**。

另外两条 3.1.54 判据：
- **`Not all shader parameters were set` 应为 0 条**（3.1.52 是 3517 条、
  3.1.53 是 1539 条），非 0 说明有多 technique 着色器漏绑参数。
- **720p 的 `D` 位必须等于 `chain`**。4K 下 `D` 位出现 0/76/103/…/180 大量小于
  `chain`，而 `细节` 分项恒为 0.00 —— 细节段认领不稳、成因未查明，见计划书 6.2①。


插件 **3.1.47** 起，每 180 帧再多打一行**引擎分项**，用来回答「引擎那 65 ms 花在哪」：

```
seg 分项 1280x720：掩码 0.29 + 磨皮 12.49 + 色调 0.00 + 五官 0.00 + 细节 1.50 + 美形 0.00 = 14.28 ms（引擎 14.28，差 0.00）
```

（上面是 2026-10-31 16:46 真机日志里的实测行，不是举例。）

- 六段顺序与 `CoreEngine::process()` 的真实执行顺序严格一致，不是事后估算。
- **先看末尾的「差」**：六项之和必须**略小于**引擎总耗时（差额 = 分支判断与循环骨架，
  通常 1~5%）。差值过大或为负，说明埋点位置错位，六个数一律不可用。
  实测 57 个窗口的差值均值只有 0.001 ms，说明埋点与总计时用的是同一时钟、无遗漏。
- 某一段为 `0.00` 可能是真的没跑（例：面板没开五官项、磨皮档位为 0），也可能是该段
  极快，两者用「差」这一项区分不了，需要结合面板参数判断。
  **判读前先读场景文件里该滤镜的实际档位**（`basic/scenes/<集合>.json`），
  否则会把「档位为 0」误读成「埋点坏了」。
- 行首的 `seg ` 是**故意**加的 ASCII 锚点：`03_装机` 下的 `.ps1` 必须纯 ASCII
  （PowerShell 5.1 按 ANSI 解码无 BOM 文件，中文会乱码），脚本只能靠 ASCII token 定位。
- 需要 `BEAUTY_PROFILE=1`（`2_run_diag.ps1` 已默认为诊断开启）。旧日志没有这一行。

配置：`beauty_test` 集合、摄像头原生 720p、面板**仅 `blur_level=100`**，其余档位全 0。

| 段 | 均值 ms | 占引擎 |
|---|---|---|
| 掩码更新 | 0.29 | 2.1% |

属于磨皮语义。磨皮 + 基准回填 = 13.99 ms = 引擎的 98%。

> ⚠ **由此更正一条旧结论**：表C 4K 那行曾推断「掩码只有 2% 却要 65 ms，说明耗时大头是

## 五、从数据得到的四条结论

1. **引擎是绝对大头，下载/上传加起来只占 11%。**
   1280×720 实机：13.91 / 15.58 = **89% 花在 CPU 像素运算**，拷贝往返只有 1.67 ms。
   → 这修正了方案 A 立项时的叙事（"消灭 8MB 往返"）。真正的收益是**省 CPU 算力**，
   拷贝只是顺带；也说明"只搬 tone 上 GPU"必然净亏（Phase 2 的判断得到数据支持）。

2. **4K 在 CPU 路径上根本不可用。**
   60.85 ms 引擎 + 15.73 ms 拷贝 = 76.59 ms/帧，是 30fps 单帧预算（33.3 ms）的 **2.3 倍**；
   实测 180 帧要跑约 25 秒 ≈ **7 fps**。这不是"慢一点"，是功能不可用。

3. **耗时随像素近似线性，但在 4K 略低于线性。**
   8.77 → 21.30 是 ×2.43（像素 ×2.25）；21.30 → 60.85 是 ×2.86（像素 ×4.0）。
   4K 段收益递减，推测是掩码 ROI 与缓存层级的关系，不影响结论。

4. **引擎耗时对"掩码覆盖"的敏感度，超过对分辨率的敏感度。**
   同为 1080×1920，脸放大 1.78 倍 → 48.73 ms；正常构图 → 21.30 ms（**2.3 倍**）。
   → **基线表必须同时记录掩码覆盖率与人脸数，否则数字不可复现。**

   > ⚠ **2026-10-31 15:44 更正**：本节原先写作「表A/表B 同为 1280×720 却差 5.14 ms，是因为
   > 美形三项在表B 没检出关键点」。3.1.44 加上覆盖率埋点后，这条解释被**证伪**：
   > 表B 的 `有脸%` 实测 96%，脸一直都在。真实原因是当时场景项被 OBS 归一化成
   > `bounds=360×360`，相机缩到画面一角，**掩码覆盖只有 1.3%**（表A 是 15.5%）。
   > 覆盖差 12 倍 → 引擎快 5 ms，与美形无关。修正后的表C 见第七节。

## 六、功耗换算（用实测数替换原来的粗估）

单帧 15.58 ms、预览 30fps → 每秒占用 **0.467 个逻辑核**（15.58 ms × 30 = 467 ms/s）。
20 线程的 255HX 上，这相当于整机 CPU 的约 **2.3%**；换算成"单核占用率"是 **47%**。
GPU 化后这部分几乎归零（人脸检测仍留 GPU/DirectML，不进这个数）。

按原规程的 `C₁ ≈ C₀ − B·f` 口径：实测 B ≈ 0.467 核，f ≈ 0.89（引擎占比）→
可消除 ≈ **0.42 个逻辑核**。之前文档里"9% → 约 4%"的推算，现在有了本机实测的比例因子，
但**具体百分比仍取决于当时的其他负载**，不要直接引用 9%→4% 这个数。

### 表C 读出来的三件事

**1. 720p 两种路径对得上，说明场景源代理在 720p 是可信的。**
摄像头直挂 15.71 ms / 掩码 15.5%，场景源 16.00 ms / 掩码 13.4%，差 0.29 ms（1.8%）。
→ 表B 那套「把滤镜挪到场景源」的方法，**只在画布尺寸等于相机原生尺寸时才成立**。

**2. 之前「表A/表B 同为 720p 却差 5.14 ms，因为美形三项在表B没检出」的解释是错的。**
3.1.44 埋点直接推翻了它：表B 的 `有脸%` 是 96%，脸一直都在。真实原因是当时场景项的
transforms 被 OBS 归一化成了 `bounds=360×360`，相机被缩到画面一小块里，
**掩码覆盖只有 1.3%**（不是 15%）。覆盖小 12 倍，引擎自然快 5 ms。
→ 这正是「不带覆盖率的性能日志不可比」的活例。

**3. 4K 那 64.95 ms 只对应 2.02% 的掩码覆盖 —— 真实 4K 人脸会比这慢得多。**
这点很关键，别把 81.18 ms 当成「4K 的上限」。4K 档相机只能按原生 1280×720 居中显示，
脸只占 2%；若覆盖达到 720p 的 15%，ROI 磨皮量会翻好几倍。
反过来说，**即便只有 2% 覆盖，4K 也要 65 ms 引擎时间** —— 说明耗时的大头是全帧算子
（色调/清晰/锐化），不是 ROI 磨皮。这条直接支持「全帧算子优先上 GPU」。

### 测量代理的固有限制（引用数字时必须一起说）

本机摄像头硬件上限 **1280×720**，所以 1080p / 4K 只能用「场景源等比放大画布」的代理。
实测下来 OBS 会把场景项的 transforms 归一化（写 `scale=1.5` 存回去仍是 `1.0`），
相机始终按原生尺寸居中显示，于是：

- 帧变大了，**脸没变大** → 覆盖率高分辨率档必然偏低（1080p 8.5%、4K 2.0%）。
- 高分辨率档测的是「**像素规模对耗时的影响**」，不是「真实 1080p/4K 人脸的开销」。

换真正的 1080p 摄像头后，表C 的 1080p/4K 行必须重测；那时 `掩码%` 应回到 10~16% 区间。
