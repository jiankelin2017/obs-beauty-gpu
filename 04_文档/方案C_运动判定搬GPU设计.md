# 方案C：运动判定搬 GPU、检测输入只在提交帧回读（2.11.0）

> **状态**：✅ 已实现并验收（默认关，`BEAUTY_MOTION_GPU=1` 开启）
> **证据**：[`../PROGRESS.md`](../PROGRESS.md) §9.29 ｜ **开关**：[`开关总表.md`](开关总表.md)
> **一句话**：S7 之后静止时检测 8 帧才提交一次，但那张 1.6 MB 的缩略图**每帧都回读**；
> 本方案把运动判定挪到 GPU 上的一张小图上（64×64 / 16 KB）做完，**只在提交帧才回读大图**。
> 配对实测 720p 往返 **0.73 → 0.47 ms（−36%）**、4K **2.22 → 1.85 ms（−17%）**，六配置 `maxdiff=0`。

---

## 1. 问题：`下载 == tdl`，而且每帧都有

S7（2.8.0）把**检测提交**从「每帧」降到了「静止时 8 帧一次」，但没人动**检测输入的回读**。
把默认臂日志逐份摊开，两项几乎逐字相等，且每帧都出现：

| 分辨率 | `下载` | `tdl`（缩略图回读） | 检测实际提交 |
|---|---|---|---|
| 4K | 0.61–1.57 ms | 0.59–1.55 ms | 每 8 帧一次 |
| 720p | 0.61–1.18 ms | 0.59–1.16 ms | 每 8 帧一次 |

也就是说：4K 往返里最大的一笔开销，是**每帧**把 640×640 RGBA（1.6 MB）搬回 CPU，
而它每帧只换来 **256 个亮度采样点**，且其中 7/8 帧的结论是「不提交」。
S4b（2.7.0）把 33 MB 砍到 1.6 MB 是对的（§9.5.3），但**「1.6 MB × 每帧」这个乘数一直没人动**。

## 2. 为什么不能「直接少回读」

运动判定（`detectPeriod()`）的输入就是这张缩略图。不回读 → 判不出动没动 → 节流瞎猜。
所以必须先给引擎**另一个**运动数据源，才敢不动那张大图。

## 3. 设计（两段式）

```
宿主每帧：
  ① beauty_thumb_build(..., read_back=false)   // 只把 640×640 画进 thumb_rt，不回读
  ② beauty_motion_sample()                     // 再缩到 64×64；stage 本帧、map 上一帧；
                                               //   拷进 mot_buf(16 KB) → beautyCoreSetMotionImage
  ③ beautyCoreDetectDue()                      // 引擎用 64×64 算 16×16 网格，回答「本帧要不要提交」
  ④ due ? beauty_thumb_readback() : nopix 帧    // 要才回读 1.6 MB；不要则一个像素都不回读
```

- **运动数据源**：从「CPU 上的 640×640 缩略图」换成「GPU 采样的 64×64 小图」。
  引擎侧 `detectPeriod()` 走新分支（`useMot`），老的 640×640 点采样路径**原样保留**。
- **判据不变**：仍是 16×16 网格、`dper`、`thr=6 / hot=3`、静止拉 8 帧，只换「256 个点从哪来」。
- **语义不变**：`nopix` 帧与今天的「缩略图帧」同语义 —— 引擎知道本帧没有全帧像素。

## 4. 三处非显然的实现决定（都是被实测逼出来的）

### 4.1 64×64 的回读必须异步

第一版是「本帧 stage、本帧 map」。`tdl` 从 0.85 掉到 0.05 ms，**总 `下载` 几乎不动**
（720p 1.10→0.90、4K 2.08→2.03）。
→ 结论：`gs_stagesurface_map()` 的成本主体是**等 GPU 队列排空**，不是 memcpy 的字节数。
16 KB 和 1.6 MB 的 map 差不多贵。

修法：双缓冲 `gs_stagesurf_t` —— 本帧 `gs_stage_texture` 进 `cur`（只排队、不等），
map 的是 `prev`（上一帧那张，早已拷完）。代价：运动信息晚一帧。
改完 720p `下载` 0.49→0.18、4K 0.78→0.21。

### 4.2 每格取「格内逐像素 |Δ| 最大值」，不是「格内先平均」

64×64 除以 16×16 格 = 每格 4×4 = 16 个像素。若先格内平均再求差，
**方向相反的位移会在同一格里互相抵消**，运动素材上 `dmot` 掉到阈值以下 → 被当成静止。
实测：运动素材 `对齐` 从 180/180 掉到 **22/180**（12%），`dper` 变成 7。

修法：新增逐像素历史 `motPrevFull_[64*64]`，每格取 `max|Δ|`。改完运动素材 `对齐 180/180`，
代价 +0.05 ms（720p 运动 1.26→1.31）。

### 4.3 `nopix` 帧必须显式告诉引擎「本帧没有像素」

`nopix` 帧上 `g_thumbPx == nullptr`，于是原来 `else if (g_thumbPx)` 那个
「把 `srcTagThisFrame` 指到环里那一帧」的分支被整个跳过 —— 3.1.10 的帧号对齐直接失效，
实测 `对齐 0/180`。

修法：新增 `beautyCoreSetNoPixelFrame(bool)`（`g_noPixFrame`），门改成
`else if (g_thumbPx || g_noPixFrame)`。改完静止素材 `对齐` 回到 13%（与关臂一致）。

> ⚠ `beautyCoreClearMotionImage()` **不能**清 `g_duePending`：宿主顺序是
> 「先问预判 → 再清小图 → 最后 `process()`」，清了等于把刚定好的结论扔掉。

## 6. 阈值与标定

**阈值一条都没改**（`THR=6`、`HOT=3`、静止 8 帧）。理由是实测两臂给出同一组结论：

| 素材 | `dper` | 对齐 |
|---|---|---|
| 静止（两臂） | 7 | 13% |
| 运动（两臂） | 0 | 180/180 |

但必须说清：**这只证明「在这批素材上分离度够」，不是「证明两条路径等价」**。
换素材、换光照、换分辨率仍要重测这一对指标（`dper` + `对齐`），这是本方案唯一的人工判据。

1. ~~**人脸快速进出没压测**~~ → **2.11.1 已压完，风险不成立**（`PROGRESS §9.31`）。
   两轮素材：先在「空场里闪出人脸」（k=1/2/4/8）上测，两臂一致但 `nopix=0` ——
   查出来是**根本压不到**：`want_thumb` 要求「当前掩码里正好一张脸（`mkfaces0==1`）
   且上一帧全认领」，空场时整段两段式分支不进，方案C 不参与。

   **结论：它的生效域只有「单脸持续在场 + 上一帧全认领」；域内 1 帧消失无损，
   域外它不参与、行为与 2.10.x 逐字节一致。**

1b. ~~**真实素材下闸门是否仍安静**~~ → **2.11.1 已验，答案是否定的，但原因不是噪声**
   （`PROGRESS §9.32`）。用一段真人出镜的真实视频（1080×1920、单人正脸说话、固定机位、

   远小于合成静止素材的 −60%。三条证据说明判动全部来自「人说话时脸在动」：
   背景最平区帧间差 **0.00 灰阶**、判定值 lag-1 自相关 **+0.782**、运动集中在人脸所在块（44.8%）。

   **根因是判据设计**：S7 用「全画面亮度变化」代理「检测结果会不会过期」，
   而说话时人脸位置没变、检测结果完全没过期。
   → 改进候选见 `§11`（聚合方式 `max` → `RMS`）。

3. **晚一帧**：异步双缓冲的固有代价。实测 `dper`/`对齐` 与关臂一致，但理论上
   「运动起始」的判断可能滞后到 +2 帧。
4. **与 5b-2c 无关**：那一节要的是**细节段 `beta`** 的归约（会改画面强度），

## 11. 后续：真实素材暴露的判据问题（2.12.0 候选）

现状的聚合是「16×16 格取格内最大 → 4×4 格均值为块 → **取 16 块的最大值**」。
「取最大」让**任何一小块**微动都能把整帧判成动，而这与「检测结果是否过期」无关。

同一批真实素材上对比四种聚合（阈值统一 6）：

| 素材 | `max`（现状） | Top4 均值 | **RMS** | 中位数 |
|---|---|---|---|---|
| 真实-说话（希望低） | 52.5%（p50 6.3） | 34.1%（p50 4.4） | **10.2%（p50 2.5）** | 0.0%（p50 0.4） |
| 合成-真运动（希望高） | 100%（p50 33.5） | 100%（p50 21.6） | **100%（p50 12.2）** | 0.0% ← 失效 |
| 合成-静止（希望低） | 3.3% | 3.3% | 3.3% | 0.0% |

**RMS 是唯一两头都对的口径**，且事件检出零代价：`drop_k1/2/4` 与 `flash_k1` 上
`max` 与 `RMS` 的判动率**都是 3.0%**，RMS 峰值 41.7 对 max 峰值 102.9（余量 7 倍）。
中位数不能用 —— 运动只占画面一部分，中位数被静止区拉平，真运动也判 0.0%。

落地要求：改的是**判据本身**，必须重跑 S7 全量验收（静止 CPU 占用、运动滞后 ≤+1 帧、
静态 `maxdiff=0`）并重新标定阈值；开关建议 `BEAUTY_DET_ADAPT_AGG=rms`，默认 `max` 保证逐字节不变。

### 11.1 落地结果（2.12.0，2026-11-04）：验收全过，但「零代价」这个说法被推翻

实现：`g_cfg.detAdaptAggRms` + `detectPeriod()` 里 16 块先收进 `m[16]`，`rms` 走
整数牛顿开方（不引 `sqrt`，避免同一素材换机器差 1）。阈值**扫描后不重标** ——
rms 下 6 已经两头都对（真实说话 p90 = 6.1、真运动 p50 = 12.2），抬到 8 只多压
5 个百分点的判动，却把真运动余量从 2.0× 削到 1.5×。

**验收（全部实测）**：

| 项 | 结果 |
|---|---|
| 真实说话判动 | 真机 **42.7% → 7.1%**（离线预测 52.5%→10.2%） |
| 真运动素材 | **100% → 100%**，`dper=0`、`nopix=0%` —— 没被误判成静止 |
| 事件（`drop_k1/k2`、`flash_k1`） | 判动率 **3.4%/3.5% → 3.4%/3.4%**、有脸率不变、`nopix` 反涨 8–9 个点 |
| 静止 CPU | 0.536 → 0.543 核（+1.3%，噪声内） |
| 静态六配置 | **`maxdiff=0`**，三组对比（默认档 / 方案C 开启下 max↔rms / rms 无副作用） |
| 端到端往返 | 同会话三臂：关臂 **1.46–1.69**、`max` **1.57–1.65**、`rms` **0.72–0.86（−50.2%）** |

**代价（新增的实测项，原设计稿没预测到）**：

```
align%（掩码与本帧同源）   68.5% → 23.5%     ← 等价于提交率
掩码年龄 p50 / p90         1 / 5  →  3 / 7
掩码位置偏差 p90           9.05 → 16.84 px
超羽化宽度（19.2 px）的帧   0.5% → 7.9%      ← 羽化 = 0.08×脸宽，2.13.0 更正
IoU 中位                   0.966 → 0.943
```

少提交一次检测 = 多沿用一帧旧掩码，这是**必然**的因果，不是 bug。
7.9% 的帧（30 fps 下约每秒 2.4 帧）掩码边界偏 16–56 px（脸宽的 7–23%）。
上面这行「超羽化」在 2.12.0 写成 2.9%，是因为把羽化当成了 0.12×脸宽（28.8 px）；
源码是 **0.08**（`beauty_core.cpp` `kMaskFeatherRatio`），**低估了 2.7 倍**。

同一节还纠正了一个判断：`max` 与关臂的往返区间**重叠**，说明老口径在真实说话
场景拿不到可测收益（2.11.1 记的 −18% 落在波动带内）。所以 RMS 不是「优化」，
而是**让方案C 在真实场景第一次真的有收益**的前提。

### 11.2 结账（2.13.0，2026-11-04）：像素换成灰阶，「看不看得见」有量了

上一节留的那一步（「磨皮区域因此错多少灰阶」）没有走录像/同帧对拍，
而是把「偏移」做成静态实验的输入：`BEAUTY_DET_OFFSET=dx,dy` 只把**掩码几何**
平移（位置在缩略图 unscale 与 `fboxOut` 之后，所以单位是全帧像素、五官不跟着动），
同一张真实帧、同一份参数、两个 d，两张截图相减。`d=(0,0)` 跑三次全部 **0.000%**。

| 口径 | 平均 ≥2 灰阶面积 | p99 | 平均 ≥4 灰阶面积 | 最差单帧 | 边界带单像素最大 |
|---|---|---|---|---|---|
| `max` @still 8 | 2.11% | 7.84% | 1.20% | 12.0% | — |
| `rms` @still 8 | 3.73% | 18.10% | 2.37% | 26.7% | 13 灰阶（自身效果 14） |
| `rms` @still 4 | 2.81% | 11.49% | 1.69% | 18.5% | — |

（综合参数；面积占「效果实际落点」，磨皮单开时小一个数量级。）

结论：代价**只落在掩码边界那条 ≈21 px 的带子里**，但落差接近「效果自身」——
是「这一块做了、隔壁没做」的台阶，不是「强度差一点」。所以它是**拖影带**，
不是均匀的强度变化。折中 `still=4` 能把超羽化压回 3.2%、往返仍 −37%（0.93 ms）。

**默认值因此仍然不动**：0.6 ms 换一层边界带伪影，在 1080p 整帧 6–20 ms 里只值 3–6%。
