## 0. 为什么它是现在最该做的一件事

2026-11-01 07:27–07:29 第一次把五官滑块打开实测（720p，`beauty_test_region` 系列场景）：

| 场景 | 五官 ms | 引擎合计 | **往返** | `S/T/R/D/W` |
|---|---|---|---|---|
| 五项全开（各 30） | **6.90 ~ 7.53** | 9.95 ~ 10.55 | **11.47 ~ 12.97** | 179/**0/0/0/0** |
| 只开祛斑 | 3.66 | 6.28 | — | 同上 |
| 只开法令纹 | 1.96 | 4.84 | — | 同上 |
| 只开眼周三项 | 1.92 | 4.87 | — | 同上 |
| **全关（对照，3.1.68）** | 0.00 | **0.65** | **1.78** | 179/**0/0/179/179** |

两条结论，比"五官本身多少 ms"更重要：

1. **五官是单段最贵的**（6.9 ms，占引擎 70%），比整条 GPU 链的往返还大 4 倍；
2. **它一开，细节与美形也被拖回 CPU**（`D/W` 从 179 掉到 0），5b-1 直绘失效（`上传 0.52`）——
   因为认领必须构成 `SMOOTH→TONE→REGION→DETAIL→WARP` 的**前缀**，R 位拿不到，后面全断。
   **总代价 ≈ 9.7 ms @720p（1.78 → 11.5），是当前链的 6.5 倍。**

> 这解释了为什么"五官用户"一直拿不到这几天所有优化的收益。它不是一个效果，是一道闸门。

## 1. 为什么必须**整段**移植

引擎的 `chainClaimIsPrefix()` 要求认领位是 flags 的前缀。五官段（REGION）在顺序上位于
色调与细节之间，所以：

```
只搬眼周 → claim = S|T            （R 缺）→ 前缀断在 R → 整份丢弃
全搬五官 → claim = S|T|R|D|W      → 前缀成立 → 细节/美形/5b-1 全部解锁
```

**任何部分移植都拿不到一分收益**。这是本设计把三段算法放在同一次立项里的原因；
切片只是实现顺序，不是可以分批上线的东西。

---

## 2. 迁移面：三段算法族

CPU 入口是 `CoreEngine::applyFaceRegions()`（`beauty_core.cpp:3225`），
按 `眼周+立体 → 法令纹 → 法令纹下瓣 → 祛斑` 的固定顺序作用在 `dst` 上。

| 族 | CPU 实现 | 形态 | 移植难度 |
|---|---|---|---|
| **A. 椭圆增益**（立体 8 个 + 眼周 3 个 + 法令纹下瓣 1~2 个） | `applyEllipses`（`beauty_region.cpp:42`） | 解析椭圆：`d = 归一化距离`，`w = 1 - smoothstep(feather,1,d)`，`acc += gain·w·(1-shade·Y/255)`，再乘皮肤掩码权重 | **低**（纯逐像素、无邻域） |
| **B. 法令纹填平** | `applyFoldRemoval`（`:101`） | 半径 `lrRadius` 的**可分离 max 滤波**得到 `LR`，`Δ = min(maxLift, slope·max(0, LR−Y))·w` | **中**（两个方向各一趟 max，边界 clamp） |
| **C. 祛斑痘** | `applySpotFix`（`:331`） | 亮度平面 + 半径 ≤6 的**盒均值**（边界 clamp、分母按实际元素数），按 `thrLo/thrHi` 判斑点并回填 | **中**（盒均值可用滑动窗口或两趟可分离） |

共同点（决定了这个设计能有多简单）：

- **全部是 ROI 局部**（`bounds_` 或脸框），CPU 侧刻意不画全帧权重图（`beauty_region.cpp` 文件头）；
- **增益是加法**，不动色相；
- 都乘同一个皮肤掩码权重 `mw` —— GPU 侧直接采样 `skinMask`（5b-2 已经把它变成 GPU 纹理）。

## 3. 契约（沿用 mask/warp 那套，别再发明新的）

**几何与常量一律由 CPU 算好，shader 只做逐像素部分。**

- 椭圆：`cx/cy/rx/ry/rot/gain/shade/feather` 由 CPU 按现有公式算出（含关键点归一化、
  脸框缩放、`g_cfg.regThreedGain` 等），以常量缓冲传入；shader 里**不出现** `kps[]`、
  不出现 `f.w/h` 的乘除。
- 为什么：五官椭圆的坐标是「关键点 → 归一化 → 乘脸宽/高 → 加偏移」的多层链，
  GPU 侧重算一遍就是第二份实现（5c 已经证明这种重复迟早分叉）。
- 顺序：**同一段内也必须逐条保序**（A 全部 → B → A 的下瓣 → C），因为 B 的 `LR` 会读到 A 的结果。

## 4. 门禁

| # | 门禁 | 判据 | 抓什么 |
|---|---|---|---|
| **R1 区域对拍**（新） | 同一帧、同一组 face/geometry，GPU 段输出 vs CPU 段输出：`maxdiff ≤ 1`，并单列「ROI 外差异」（必须 0） | 三族算法与顺序 |
| R1b 分段对拍 | 四项分别单独开（`threed` / `eye+pouch` / `naso` / `spot`），每项各一条 | 定位到具体算法族 |
| M2/M3/M4 | 既有磨皮/细节/绘制对拍 | 链没被碰坏 |
| C1 claim | `S/T/R/D/W` 五项全满、`上传 0.00` | 前缀成立、5b-1 解锁 |

**R1 必须是"整段对拍"而不是逐项**：顺序错（比如 B 放在 A 之前）会让每项单独都对、合起来不对。

## 6. 风险

**P1 顺序耦合**。`applyFoldRemoval` 的 `LR` 是**当前 dst** 的邻域最大值，而 A 族已经改过 dst。
GPU 侧必须保证 B 读到的输入与 CPU 读到的一模一样（同样的 A 输出）。→ 4a/4b 必须串行渲染，
不能为了并行把 A 与 B 合并成一趟。

**P2 边界 clamp**。B 的 max 与 C 的均值都在 ROI 边界做 clamp（重复边缘），
分母按**实际参与元素数**算（C 的注释里记过一个真 bug：分母写成 `win×win` 时边缘整片判成斑点）。
GPU 侧要照抄这两条。

**P3 只有单脸**。与 mask/warp 一致：多脸整帧回退 CPU（先例已立，且多脸时 8 个椭圆 × 2 张脸
会让常量缓冲翻倍）。若要支持多脸，按脸循环、每脸一趟。

**P4 关键点不可信**。CPU 在 `!kpsSane(f)` 时跳过四项、只做祛斑。宿主必须拿到同一个判据
（放在 `BeautyRegionGeom.hasKps`），否则 GPU 会往脸颊/背景上糊亮度 —— 比不做更糟。

**P5 与 5b-1 的交互**。五官原来会强制回读（`dst` 被写）。认领 R 之后**不再回读**，
但 `chain_direct` 的判据是「flags 全认领」，所以 4d 之后五官用户才第一次走直绘。

**P6 参数纹理 + `SampleLevel` 的方言风险（4a 新增）**。椭圆列表走一张 64×1 RGBA32F
参数纹理，循环里用 `SampleLevel(..., 0)` —— 因为 `Sample` 是梯度指令，放在迭代次数
随运行期变化的循环里 fxc 直接拒绝（X3511「无法展开循环」，2026-11-01 第一次门禁就红了）。
`SampleLevel` fxc 能过，但 **OBS 自研 effect-parser 对它的支持没有源码可查**（本机只有头文件与库）。
→ 第一次进 OBS 时**先看日志有没有 effect 解析失败**；如果 OBS 不认，退路是把参数表改成
```
常量缓冲 + 每趟固定 8 个椭圆（分两趟画），代价是多一次全帧 pass。
```

## 9. 切片 4b 的实际结论（2026-11-01 07:45）

法令纹（family B）已并入同一支 `region.hlsl`，共 4 个 technique / 4 个像素入口：

| 入口 | 条指令 | 作用 |
|---|---|---|
| `PS_Region` | 79 | 椭圆增益（4a） |
| `PS_FoldMaxH` | 30 | 亮度平面横向邻域 max |
| `PS_FoldMaxV` | 27 | 纵向邻域 max → LR |
| `PS_FoldApply` | 92 | `Δ = min(maxLift, slope·(LR−Y))·gate·wgt·max(mw,wgt)` 并取整加回 |

门禁扩到 **A–N 14 项 + fxc 5 入口**，全绿。**新增的 `[N]` 也做过变异自证**：
`max(mw, wgt)` 改成 `mw*wgt` → FAIL；去掉 `min(..., fMaxLift)` 封顶 → FAIL。

两个刻意的取舍（都写进 shader 注释了）：

1. **max 滤波用 Clamp 采样而不是"跳过"**。CPU 是 `if (k<0||k>=ew) continue`，GPU 用 Clamp 会重复
   边缘像素 —— 对 **max** 而言结果不变（窗口一定包含边缘像素本身），所以这条差异无害；
   换成均值就必须照抄"跳过"，否则分母会变（祛斑的盒均值正是这种情况，见 4c）。
2. **三趟全帧 pass**（H / V / Apply）而不是把 ROI 抠出来画。三条 pass 都是简单的逐像素运算，
   4K 下合计约 0.5~0.8 ms，远低于 CPU 的 1.96 ms @720p（4K 按像素比会是十几 ms）。

## 10. 切片 4c 的实际结论（2026-11-01 07:50）

祛斑（family C）也已并入，`region.hlsl` 现在 **7 technique / 7 像素入口**，全是单趟通量：

| 入口 | 条指令 | 作用 |
|---|---|---|
| `PS_Region` | 79 | 椭圆增益 |
| `PS_FoldMaxH` / `PS_FoldMaxV` / `PS_FoldApply` | 30 / 27 / 92 | 法令纹（max → LR → 施加） |
| `PS_SpotSumH` / `PS_SpotMeanV` / `PS_SpotApply` | 30 / 38 / 33 | 祛斑（行和 → 真均值 → 施加） |

门禁 **A–O 15 项 + fxc 7 入口**，全绿；`[N]`/`[O]` 都做过变异自证（共 4 处改动各被抓）。

**与法令纹相反的一个选择**：祛斑的均值**不能**用 Clamp 采样偷懒 —— Clamp 会重复边缘像素，
对 `max` 无害、对**均值**会系统性偏；所以它走「行和 → 列和 ÷ 实际元素数」两趟，
分母是 `nx*ny`（CPU 注释里记过：写成 `win²` 会让 ROI 四边整片被判成斑点）。

三族的**顺序**仍由宿主保证：椭圆 → 法令纹（max/施加）→ 椭圆下瓣 → 祛斑。
现在缺的只有「把三族串起来 + 引擎几何快照 + R1 对拍」这一步（4d）。

### 首跑抓出的两个 bug（都只有逐像素对拍能抓到）

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | `maxdiff=6 / 8.4% / avg 1.6` | `PS_Region` 里 `Y` 用 **0..1** 的 `src` 算，而 CPU 的 `Y` 是 **0..255** 域 → `(1 - shade·Y/255)` 几乎失效，所有 `shade>0` 的椭圆都偏亮 | 统一走 `lumOf(src)`（先 `floor(c*255+0.5)` 回到字节域） |
| 2 | 同上（修完仍 `maxdiff=6 / 6%`） | 参数纹理采样写成**纹素坐标** `(k*3+0.5, 0.5)`，`SampleLevel` 吃的是**归一化 UV** → 全被 `Clamp` 夹到最后一个 texel（全 0）→ **GPU 一个椭圆都没加**，差异量恰好等于 CPU 的效果量 | UV 除以 `REGION_PARAM_W`（与宿主建纹理的宽度一致） |

两条都写进了静态门禁，并且**变异自证**：
`Y` 改回 0..1 域 → `[K]` FAIL；去掉 `/ REGION_PARAM_W` → `[L]` FAIL。

> 这两条正好说明「静态门禁 + 逐像素对拍」是互补的：门禁能编译、能查公式抄写，
> 但**域（0..1 vs 0..255）**和**UV 归一化**这类问题，只有真跑一遍比较才现形。

### 还剩

法令纹（邻域 max + 顺序耦合）与祛斑（盒均值）两族的 R1；都通过之后才允许
`claim |= BEAUTY_SEG_REGION` —— 那一步才会把 `S/T/R/D/W` 补全、5b-1 直绘恢复。

三趟整段对拍：`maxdiff=0 / 1 / 1`、差异像素 `0 / 1 / 3`（≤0.0003%）；

### 首轮抓出的 5 个 bug（每个都对应一条「只能靠真跑发现」的教训）

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 输出全黑，`maxdiff=255`/100% | 自己套 `gs_technique_begin_pass`，与 `smooth_draw` 内部的 pass 嵌套 | 只绑参数，pass 交给 `smooth_draw` |
| 2 | `Not all shader parameters were set`，该趟静默跳过 | 漏绑 `ellipseCount`（随趟变化：主 14 / 法令纹 2 / 下瓣 2 / 祛斑 0） | 每趟重绑（E2） |
| 3 | 2.8% 像素、差异铺满 ROI | 祛斑横向「和」到 3315，/255 后是 13，存进 **8 位 UNORM** 饱和成 1 | 中间 RT 改 **GS_RGBA32F** |
| 4 | 同上（修完 3 仍 2.8%） | CPU 的盒均值在 **ROI 边界** clamp，我按画面边界算 | 加 `roiMin/roiMax`，窗口与 `nx*ny` 都按 ROI |
| 5 | OBS 里 `Expected 'type'`（fxc 能过） | OBS 解析器不接受**一行两个 uniform** | 一行一个 |

后 4 条里有 3 条是「**静默**」的：不报错、不崩，只是画面略偏 —— 正是设计稿 §4 要求
「整段对拍 + 分段对拍」的原因（分段把 2.8% 定位到祛斑，整段确认顺序没错）。

### 还剩最后一步

`claim |= BEAUTY_SEG_REGION`：把链钩子里的 `region_blocks`（当前无条件阻止认领 DETAIL）
换成「GPU 三族都成功才认领」，此后五官用户第一次拿到 `S/T/R/D/W` 全满、
5b-1 直绘恢复。预计 720p 往返 **11.5 → 约 2.0 ms**。

## 14. 认领 REGION —— 五官 GPU 化完成（2026-11-01 08:10，3.1.72）

钩子在**色调之后**调用 `beauty_region_chain()`（与 R1 对拍**共用同一个函数**，
所以验的就是跑的那一份）。三族全部成功才 `claim |= BEAUTY_SEG_REGION`；
任何一步失败都不认领，引擎把五官连同细节/美形一起交回 CPU（画面正确，这一帧慢）。
退路 `BEAUTY_GPU_REGION=0`。

| 分辨率 | 项 | CPU 五官 | **GPU 五官** | 倍数 |
|---|---|---|---|---|
| 720p | 往返 | 11.47 | **1.58 ms** | 7.3× |
| 4K | 往返 | 49.34 | **8.88 ms** | **5.6×** |
| 4K | `S/T/R/D/W` | 180/0/0/0/0 | **180/0/180/180/180** | 首次五项全满 |
| 4K | `上传` | 5.34 ms | **0.00** | 5b-1 直绘恢复 |

4K 关掉 GPU 五官时 49.34 ms 的构成：磨皮 10.07 + 五官 7.94 + 细节 2.48 + **美形 13.32**
（被拖回 CPU）+ 下载 7.43 + 上传 5.34 —— **一次五官就能把整条链打回原形**，
这也解释了为什么它是"一道闸门"而不是"一个效果"。

### 从 6.9 ms 到 5.6 倍：这一段的完整账

| 阶段 | 720p 往返 | 4K 往返 |
|---|---|---|
| 五官全在 CPU（3.1.68） | 11.47 | 49.34 |
| 五官三族上 GPU 并认领（3.1.72） | **1.58** | **8.88** |

至此移植的**五段全部跑在 GPU** 上，`S/T/R/D/W` 可以五项全满。

## 15. 3.1.73 处置：五官与帧环改回 opt-in（2026-11-01 08:16）

### 发生了什么

v3.1.72 默认开 GPU 五官 + 显存帧环，4K 会话跑了约 5 分钟后 **OBS 崩溃**：

- 崩溃点 `nvwgf2umx.dll`（NVIDIA 驱动）`c0000005`，时间 08:10:12；
- **崩前 1 秒**日志：`device_copy_texture (D3D11): Source and destination must have the same dimensions`
  —— 来自帧环的 `gs_copy_texture`；
- 崩前 2 秒：`五官整段对拍 3840x2160：maxdiff=2 差异像素=417`（此前的对拍都是 0~3 px）。

崩溃线程栈全在驱动内，但其它线程栈里有本插件 + `d3d11` 的绘制帧。**根因未定**。

### 已做的处置（3.1.73）

| 改动 | 原因 |
|---|---|
| 帧环 `put` 前逐张核对尺寸/格式，不一致就跳过 | 消灭上面那条 `device_copy_texture` 错误（画布/源尺寸在会话中会变） |
| 帧环槽位 3 → 2 | 4K 每张 33 MB，省 33 MB 显存 |
| **帧环、GPU 五官改回 opt-in**（`BEAUTY_GPU_FRAME_RING=1` / `BEAUTY_GPU_REGION=1`） | 根因未定前不默认跑（**2.14.0 起五官已重新转默认开，见文首**） |
| 五官中间层 RT `RGBA32F` → `R32F` | 4K 每张 66 MB → 16.6 MB（两张合计省约 100 MB） |

3.1.73 装机后 720p 复跑正常：`S/T/R/D/W=180/0/0/180/180`、往返 **1.80 ms**、无新崩溃文件。
